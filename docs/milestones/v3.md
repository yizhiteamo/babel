# V3 Milestone — Immersive Game Translation

## Status

Active — the three spikes hold; the skeleton runs end to end on a real game.

## Goal

Add low-latency translation for dynamic game content, drawn to fit the game's
interface, while reusing the common translation architecture.

## Spikes first

The design rests on three platform facts nobody has measured. Each is a small
throwaway experiment on the phone; if one fails, the feature definition changes
before any of the work below starts.

- [x] **Window screenshots.** `takeScreenshotOfWindow` on a running game: is
  Babel's own overlay absent from the picture, how often can it be taken, and
  does the game block it? — **holds** (results below)
- [x] **Horizontal OCR on game text.** The on-device general engine over
  `material-sample/game/`: accuracy and time per screenshot, and whether the
  "do not translate" rules separate dialogue and buttons from numbers and logos.
  — **holds**, with three faults to design around (results below)
- [x] **Tap pass-through.** A touchable translation that hands a short tap on to
  the game with `dispatchGesture` and shows the original on a long press: how
  long the hand-off takes, and whether games accept the injected tap. — **holds**,
  with one ordering rule that must be kept (results below)

## Spike 1: window screenshots (2026-10-07, phone, Android 15)

Blue Archive (Unity, `com.YostarJP.BlueArchive`) in a story scene, landscape,
with manga mode on so Babel's translations were drawn over the dialogue. A
temporary probe in the accessibility service took one whole-display screenshot
and then window screenshots of the game's application window.

| Question | Answer |
|---|---|
| Is Babel's overlay in the picture? | **No.** The display screenshot shows the translated dialogue and buttons; the window screenshot of the same moment shows the original Japanese, untouched. |
| Resolution | Full: 3200×1440, same as the display |
| Time per screenshot | **60–110 ms** |
| How often | **About every 333 ms**, the same limit as whole-display screenshots: requested ~205 ms apart, every other one failed with `ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT`; ~300 ms or more apart, all succeeded |
| Does the game block it? | No |
| Window list | The game is one `TYPE_APPLICATION` window (title ブルアカ); Babel's overlays are separate windows above it, so picking the game's window is unambiguous |

Consequences for the design:

- The core premise holds: once a translation covers the original, the next
  line is still visible to Babel, with **no clear-and-recapture** — the cost
  manga mode pays on every page turn is gone for game mode.
- Frames arrive at ~3 per second, so a finished line is seen within ~333 ms;
  the stability check ("two frames the same") costs at most ~666 ms. That is
  the floor of the latency budget, before OCR and translation.
- **Recognising a game needs package visibility.** Asking the package manager
  for the game's category failed (Android 11+ hides other packages). The
  manifest needs a `<queries>` entry before "only in games" can rely on
  `ApplicationInfo.category`.
- In passing, manga mode run on this game showed why games need their own path:
  both `AUTO` and `MENU` came back as 菜单, and a 正在加载…… appeared where the
  ▼ continue mark is. The manga recogniser and detector are not for game UI.

## Spike 2: horizontal OCR on game screenshots (2026-10-07, phone)

`GameOcrMeasurementTest`: ML Kit's Japanese model over the five screenshots in
`material-sample/game/`, each scaled to the phone's 3200×1440, three timed runs
after a warm-up. The backdrop signals were then computed off the device from
the same images and the returned boxes.

**Time for a whole frame:** 150–210 ms for a story scene (4 lines), 300–430 ms
for the lobby (33 lines). Recognition time follows the amount of text, so
reading only the region that changed is also the way to keep it short.

**What it read:**

| Screen | Result |
|---|---|
| Dialogue (ba-004) | The line exactly right. Speaker and affiliation came back as **one line** (ツムギワイルドハント芸術学院) |
| Choices (ba-003) | Both exactly right, except `……` read as `。`/`…` |
| Pop-up body (ba-002) | Line 1 exact; line 2 dropped one character (糸巻き → 巻き) |
| Character bubble (ba-001) | Exact, `……` dropped |
| Small icon labels (ba-001) | Most right; four misread or merged (モモトーク → 藍トーク, two labels joined) |
| Yellow outlined lettering (ba-002) | Badly misread (イペントアイテムを種得) |
| Logo (ba-005) | Misread, and boxes 8–29% of the screen high |

**"Do not translate" — the signal works.** For each line, predict the band just
above and below it by interpolating, row by row, between the pixels at its left
and right ends; the mean error says how plain its backdrop is. It is also
exactly the test of whether erase-and-redraw will look clean.

| Text | Interpolation error |
|---|---|
| Choices, pop-up body, pop-up title | 0.2–0.9 |
| Dialogue line, speaker line, bubble | 4–7 |
| Interface labels on plain bars | 1.3–5 |
| Stylised lettering, banner text, labels drawn on icons | 14–68 |
| Logo | 26–59, and over 7% of the screen high |

A threshold near 12, plus line height under ~7% of the screen, plus the number
and short-Latin rules (155/240, 264,410,355, 17:13, Lv. 90, AUTO, MENU, MAX),
put every line in the right group on these five screens: dialogue, choices,
pop-ups and plain labels translated; logos, stylised lettering, art-drawn labels
and numbers left alone. Five screens of one game prove the signal, not the
threshold — it is to be checked on other games.

**Three faults to design around:**

- **Lines of different style merge.** Speaker and affiliation are one "line" to
  the engine. Drawing them back needs splitting on colour and gap, and the
  speaker name is worth knowing separately for dialogue context.
- **Small drops and ellipses.** A missing character or a lost `……` passes
  straight into the translation. Reading the same line on two consecutive
  frames — which the stability check does anyway — gives a second reading to
  compare, at no extra capture cost.
- **Misread labels are on art.** The labels it got wrong are the ones the
  backdrop rule already skips, so the error does not reach the screen.

## Spike 3: tap pass-through and long press for the original (2026-10-07, phone)

A temporary probe in the accessibility service put a touchable stand-in
translation (`TYPE_ACCESSIBILITY_OVERLAY`) over Blue Archive's dialogue box,
and taps were sent with adb. To hand a short tap on, the window makes itself
`FLAG_NOT_TOUCHABLE`, injects a tap at the same point with `dispatchGesture`
(capability `canPerformGestures`, which the service config does not yet
declare), and becomes touchable again 150 ms later.

**The game accepts the injected tap.** Each tap advanced the dialogue by one
line, exactly as tapping the game does.

**The trap, measured:** turning the window untouchable takes about **80 ms** to
reach the input system. Inject sooner and the tap lands on Babel's own window
again, which then hands it on a second time:

| Wait before injecting | Taps handed on, for 3 adb taps |
|---|---|
| 0 / 16 / 32 ms | 6 — each tap caught once by Babel's own window |
| 50 ms | 5 |
| 80 ms | 3 — correct |

**The fix that also removes the latency:** make the window untouchable **at
touch-down**, not at release. The rest of a touch that started on a window
keeps going to that window, so the press and release still reach Babel; only
the injected tap that follows goes through. A human tap lasts long enough for
the change to land:

| Tap held for | Taps handed on (of 3) | Release → game receives the tap |
|---|---|---|
| 80 ms | 3 | 25–30 ms |
| 120 ms | 3 | 18–28 ms |
| adb's ~10–40 ms | too many | — |

So the rule for the real thing: untouchable at touch-down; at release, inject
at once if at least ~80 ms have passed since touch-down, otherwise wait until
they have. A normal tap then costs the player **~20–30 ms**; only the shortest
flick costs up to ~100 ms.

**Long press for the original works.** Held for 2.5 s: after 450 ms the stand-in
became transparent and the game showed through; on release it came back, and no
tap reached the game, so a long press never advances the dialogue.

## Skeleton: end to end on a real game (2026-10-07)

Game mode as a third switch on the home screen; `:platform:game`
(`GameTextSource`) reads the game's window, `GameTextFilter` drops what is not
worth translating, `StableLines` publishes a line when two frames agree, and
the common coordinator and overlay do the rest. Lines are drawn in the existing
box for now — erase-and-redraw and tap pass-through come next.

- **Recognising a game works.** Blue Archive declares `CATEGORY_GAME` (0), read
  through the manifest's `<queries>`. Manual add for games that do not declare
  it is still to do.
- **Translated, end to end**, on four advances of the story: speaker line,
  dialogue lines and the AUTO/MENU buttons (自动, 菜单).

**Latency, from the tap to the translation drawn** (remote chat provider):

| Advance | Tap → line settled | Settled → translated | Total |
|---|---|---|---|
| 1 | 1.76 s | 0.63 s | **2.4 s** |
| 2 | 1.87 / 2.38 s (two lines) | 0.57–1.07 s | **2.9 s** |
| 3 | 2.14 / 2.66 s (two lines) | 0.62–0.92 s | **2.8–3.6 s** |

Where the time goes, and what each fix is worth:

- **A frame every ~470 ms, not 333.** Capture (~80 ms) and recognition
  (160–360 ms) run one after the other, so the loop is slower than the
  platform allows. Taking the next picture while the last is being read brings
  it back to ~333 ms.
- **Settling costs a frame after the line is complete**, by design; at 333 ms a
  frame that is ~0.35 s instead of ~0.5 s. Part of "tap → settled" is the game's
  own typewriter animation, which no reader can shorten.
- **Reading only the region that changed** cuts recognition from 160–360 ms to
  the dialogue box alone.
- **Translation 0.57–1.07 s** is the provider; a cached interface label is 0 ms.

**Faults seen, for the next steps:**

- Speaker and affiliation are still one line (ツムギワイルドハント芸術学院), and
  translate badly as one. Splitting on colour and gap is needed.
- Two lines of one utterance are translated separately; they should be joined
  into one translation unit, as manga mode joins a balloon's lines.
- The existing box is opaque black and does not fit the game's panel — the
  erase-and-redraw step.
- Game mode reads continuously while a game is in front (OCR every frame, about
  half of one core); throttling when nothing changes is still to do.

## Where manga mode and game mode met (2026-10-07)

Three conflicts between V2 and V3, each confirmed on the phone and fixed:

- **Manga mode read games.** With game mode off, the comic recogniser read
  Blue Archive's screen (AUTO and MENU as 菜单, an invented loading line).
  A declared game is now game mode's alone: manga mode skips it whether game
  mode is on or not (`image scan skipped: a game, which is game mode's`).
- **A tap on a game translation was swallowed.** Game lines were drawn in
  manga mode's touchable windows, where a tap toggles the original. Game
  translations now hand a short tap on to the game (`TapForwarder`,
  `dispatchGesture`) and show the original while long-pressed, with the
  window untouchable from touch-down (spike 3's rule). Measured: a tap on the
  dialogue advanced it, a tap on a translated choice chose it, a 1.5 s press
  showed the original and did not advance.
- **The quick-settings tile ignored game mode.** It now pauses and restores
  game mode with the other two.

Seen in passing: the speaker label (通行人A) was not translated — to look at
with the speaker/affiliation split.

## Faster: frames at the platform's pace (2026-10-07, phone)

Two changes, measured on Blue Archive with six story advances each time:

- **The next picture is taken while the last is read** (`GameTextSource.read`
  runs its own loop and prefetches the next window frame).
- **Window frames are paced start to start.** The pacing counted 400 ms from
  when the last picture *arrived*, so a capture's own 60–110 ms was added to
  every frame. Window frames are now asked for 350 ms after the last was asked
  for, which spike 1 showed the platform allows; no capture was refused in 110
  frames.

| | Before | After |
|---|---|---|
| Frame interval, median | 484 ms | **351 ms** |
| Tap → line settled, median | ~2.1 s | **~1.5 s** (1.23–1.75 s; one outlier at 4.4 s across a scene change) |

Part of "tap → settled" is the game's own typewriter animation, which nothing
on Babel's side shortens.

**Reading only the changed band did not pay off in this game.** The frame is
compared on a 64×29 brightness grid, and only the rows that changed are read
again (`ChangedBand`). Blue Archive's characters and backdrop are animated even
while nothing is said, so 88 of 111 frames changed over more than half the
height and were read whole; 17 were unchanged and 6 read as a band. It stays —
it costs a scaled bitmap per frame and helps any game with a still scene — but
the speed above comes from the pacing, not from it.
