## Two defects found by a user, after V1 was called complete

**Pause was implemented but unreachable.** "Translation stops/pauses cleanly" is
ticked above, and it was true of the code: `TranslationCoordinator.pause` works
and is tested. Nothing in the interface ever called it, so the only way to stop
translating was to switch the accessibility service off in system settings —
and the permission card hid its own button once granted, so the app offered no
route there either. The item was true of the domain and false of the product.

Worth remembering when ticking an acceptance item: a capability nobody can
invoke is not a capability the user has.

Now exposed as pause/resume, using the coordinator's existing semantics —
translations already drawn stay until the content changes, which is why the
control says "pause" rather than "off". The permission card keeps a route to
system settings whether or not the permission is granted.

**The home screen did not scroll.** The root `Column` had `fillMaxSize()` and no
`verticalScroll`, so on any screen shorter than the content the bottom was cut
off with no way to reach it. Manga mode sits last, so its button was simply
unreachable — reported from a device and reproduced at 1920x1080 landscape.
Portrait on the test emulator was tall enough to hide the problem entirely,
which is also why the advice given before the report ("scroll to the bottom")
was wrong.

Verified after the fix, at the resolution that failed: the page scrolls, manga
mode starts, pause stops translation (11 scans, 0 translations, 0 renders) and
resume restores it (8 scans, 8 translations). V1 itself is unchanged — 7 text
nodes on the first screen and no `ClearAll` while scrolling, both matching what
is recorded above.

### A third defect, from shipping the second fix

Exposing pause turned out to pause everything. One coordinator serves both
acquisition paths, and its paused branch dropped every incoming element
regardless of source — so with text translation paused, manga mode recognised
text and rendered none of it. Reported from a device and reproduced: 18 lines in
11 regions, 0 translations.

The control said "text translation" and the behaviour was global. The label was
the lie, but relabelling was the wrong fix: reading a comic would then require
resuming text translation, which translates every app the user opens — and the
two paths are mutually exclusive anyway, so the path just resumed would be
suspended again immediately.

Pause now applies to the text path only, decided per element by `sourceType`
rather than per batch, so a mixed batch cannot lose half of itself quietly.
Measured on the same steps: 19 lines in 12 regions, 12 translated, 12 rendered,
with text translation still showing paused — and with 2 accessibility scans
arriving in the same window and producing no text translations, which is what
makes that a real check rather than an empty one.

## Platform constraints found on device

These are Android behaviours, not defects. They bound what V1 can do:

- **Full opacity and touch passthrough are mutually exclusive.** Android caps a
  touch-passthrough overlay at `maximum_obscuring_opacity_for_touch` (0.8 by
  default) because a see-through-but-unclickable overlay is the shape of a
  tapjacking attack. Removing `FLAG_NOT_TOUCHABLE` restores full opacity but
  makes the whole screen unclickable and unscrollable. Verified by experiment in
  both configurations. Passthrough was chosen, so roughly a fifth of the source
  text shows through. A window-level alpha cannot be compensated for in the view
  hierarchy — it applies after the window is composited.
- **Matching the source background is impossible in V1.** The leftover strip
  where a translation is shorter than its source shows `0.8 × ours + 0.2 ×
  theirs`, so a background close to the app's own would blend in — but
  `AccessibilityNodeInfo` exposes no colours and sampling the screen needs
  MediaProjection, which V1 excludes.
- **Settings-style apps hide overlays entirely** via
  `setHideOverlayWindows(true)`. Acquisition and translation still run; only
  rendering is suppressed.
- **Passwords never reach the pipeline as plaintext.** Verified on device: a
  17-character password is exposed to accessibility as 17 `U+2022` bullets. The
  masked-text rule in `DefaultSensitiveContentPolicy` covers that form, and the
  password setup screen exposes nothing to accessibility at all.

## Third-party verification

Verified against Chromium rendering `docs/testing/reading-sample.html` — a
text-heavy English page. WebView matters because its accessibility tree comes
from Chromium, not from code in this repository.

It immediately exposed two real defects that native UI had hidden (both fixed):
type size was derived from bounds height as though that were a line height, so a
four-line paragraph collapsed onto one illegible line, and a container node
reporting the height of the whole WebView produced display-sized type across
half the screen.

After the fix: 7 nodes for the first screen, paragraphs rendered multi-line at
readable size, and 4 swipes produced 6 scans, 5 Hide events and no ClearAll.
A sentence repeated twice on the page kept two independent overlays, so identity
by occurrence index holds under Chromium's tree as well.

## Touch passthrough

Verified by controlled experiment against `docs/testing/touch-link.html`, whose
link is long enough to carry an unmistakable overlay.

The link was first confirmed covered — a screenshot showed the translation, not
the English source, occupying the link's bounds. Then the same coordinate was
tapped in two builds:

| Window flags | Tap on the covered link | Outcome |
|---|---|---|
| with `FLAG_NOT_TOUCHABLE` | navigates to `touch-target.html` | touch passes through |
| without it | stays on `touch-link.html` | overlay swallows the touch |

The second run is what makes the first meaningful: identical coordinate,
identically covered, opposite results. Without it, a tap that worked would not
rule out the overlay simply not being there — which is exactly how an earlier
attempt at this check produced a false pass.

The counter-test also reproduced the opacity finding from the other direction:
with the flag removed the overlay rendered fully opaque, the source text no
longer showing through.

## Operational notes

- Reinstalling the APK leaves the service listed as enabled and even "bound",
  but it stops receiving events. It must be toggled off and on again.
- `am force-stop` kills the service and the system does not restart it.
- Enabling the service through `settings put` is unreliable; granting it through
  the system UI works.
