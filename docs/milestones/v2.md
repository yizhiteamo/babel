## Acceptance testing method

Settled before V2 starts, so the work is not designed around a test that cannot
distinguish OCR from accessibility.

**Material must be an image.** `docs/testing/manga-page.html` contains nothing
but an `<img>` pointing at `manga-sample.png`. Live HTML text would be read
straight off the accessibility tree and the run would prove nothing about OCR.

Confirm this holds before trusting any result. The check is **not** "zero text
nodes" — the browser's own tab title and address bar are still text, and were
measured as 2 nodes. The judgement is that **no Japanese reaches acquisition**:
no node inside the page content area, and nothing containing kana or kanji.
Verified on device — both nodes were browser chrome, zero contained Japanese.

`manga-sample.png` is generated from `manga-source.html` by rendering it on
device and screenshotting, so it carries real glyph rasterisation rather than
synthetic shapes, without using copyrighted material. Real manga screenshots may
be used for judging quality, but are not committed.

Observe: bubbles detected, reading order, character accuracy, bounding-box
quality, and whether the masked area matches the sampled background.

## OCR feasibility (probed before V2)

`MlKitJapaneseOcrProbeTest` ran against the sample on the GMS-less emulator.

**Viable**: the Japanese recognizer runs without Google Play Services and does
read vertical text — 83% average character overlap across four bubbles.

**But its output cannot be used as translation units**, which shapes the
acquisition design:

- Columns are returned left-to-right; Japanese vertical text reads
  right-to-left. `今日はいい天気` came back as `いい天気今日は`.
- Bounding boxes are per column (38–95px wide), never per bubble. One bubble
  split into two blocks.
- Entire columns can be missed (`明日の会議`), and similar glyphs get confused
  (駅→統, 待→侍).

This confirms "text-region detection" and "speech-bubble-aware layout" are
load-bearing scope items: grouping columns into bubbles and rebuilding reading
order from box geometry is required work, not polish.

**Line granularity is sufficient.** A later probe printed `block.lines`, and
columns *are* separated there even when the enclosing block concatenates them
in the wrong order:

```
[3] box=(1156,122-1251,282) text=いい天気今日は      <- block, reversed
    line[3.0] x:1157-1193   text=いい天気
    line[3.1] x:1215-1251   text=今日は            <- further right, reads first
```

So reading order is fully recoverable from geometry, and `TextRegionGrouper`
does exactly that: group by adjacency, then sort columns by right edge
descending. Grouping also rejoins a bubble that arrived as two blocks.

One trap only real coordinates reveal: bubbles sharing a row are not aligned to
the pixel — the top-right bubble starts at y=122 while the top-left starts at
y=101. Ordering regions by top and then by right therefore reverses the page.
Rows are formed from vertical overlap first.

**The engine reports orientation directly.** `Text.Line.angle` came back as
88.6°–92.0° for every vertical column — a definite signal, so orientation is
never guessed. Shape (tall vs wide box) exists only as a fallback for
recognisers that report no angle, and is strictly weaker: a single character is
square and tells shape nothing, while its angle is just as clear.

`line.elements` turned out useless for this: ML Kit returns one element per
line holding the whole column, so character-level layout analysis is not
available.

Orientation is resolved **per line, not per page**. Comics mix vertical
dialogue with horizontal captions, and adjacency itself is orientation-
dependent — grouping the two together would corrupt the bubbles, not merely
their order.

**Known quality ceiling.** Desktop tools use manga-specific recognisers
(48px models, manga-ocr); ML Kit is general-purpose. If accuracy on real
material proves unacceptable, replacing the recogniser is a higher-priority
improvement than better erasure — a wrong character hurts reading more than a
faint ghost does.

## Screen capture

MediaProjection is not optional infrastructure that could be swapped for
something lighter — the platform dictates its shape:

- A projection cannot run outside a **foreground service** (Android 10+), and
  from Android 14 that service must declare `mediaProjection` as its type and
  hold `FOREGROUND_SERVICE_MEDIA_PROJECTION`.
- The service must reach the foreground **before** `getMediaProjection` is
  called; the reverse order throws.
- From Android 15 the user re-consents for **every** session and the token
  cannot be stored, so there is nothing to cache and no way to start capture
  silently.

The mandatory notification is a benefit rather than a cost here: it is the
user's standing indication that the screen is being read, which is what
`docs/systems/privacy.md` asks of anything touching screen content. Frames are
never written to disk and diagnostics log dimensions only.

Verified on device: session active at 1920x1080, virtual display created at 280
dpi, foreground service running with `types=0x00000020`
(`FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION`), a first frame actually retrieved,
and both service and virtual display released on stop.

The service performs a first-frame self check after starting, because a virtual
display can exist while its reader never fills — "session created" is not the
same as "frames arrive".

## Pipeline end to end

Capture → OCR → grouping → translation → rendering runs on device. Measured on
`manga-page.html`: 28 lines recognised in 19 regions, translations rendered over
all four bubbles. No change was needed in the translation core — normalising
every source into `TextElement` before it enters the pipeline (ADR 004) is what
made adding OCR an additive change.

**A static screen produces no frames.** `acquireLatestImage` returns null unless
the display changed, and a comic page is static by definition — reading on
demand works on video and fails on exactly the content V2 targets. Frames are
therefore cached from an `OnImageAvailableListener`, and `latestFrame` hands
back a copy because recognition is asynchronous and a new frame could recycle
the one being read.

**Both acquisition paths feed the same coordinator**, so accessibility scanning
is suspended while a capture session is active. Without that the same screen is
translated twice and two layers of overlays stack up.

### Known gaps, visible in the first end-to-end screenshot

Expected at this stage — erasure and re-layout are later items — but recorded so
they are not rediscovered:

- **Overlay colour does not match the page.** The device is in dark mode, so
  overlays render dark over a white comic page. This is precisely what ADR 008's
  background sampling is for, and it is not implemented yet.
- **Translations are squeezed into vertical column bounds**, two or three
  characters per line. "Translation re-layout" has to give a translated bubble
  the whole bubble, not the source column's footprint.
- **OCR reads the whole screen**, including browser chrome, so UI text gets
  translated alongside the comic.
- **Translation quality is poor** on these samples — partly OCR error
  (駅→統, 待→侍), partly on-device translation of short fragments. Consistent
  with OCR being the known quality ceiling.

## Sampling the background, and when to recognise at all

Overlays now take their colours from the page. The acquisition layer is the only
part of the system that ever sees pixels, so it samples them and passes them
down as `SourceStyle`; accessibility leaves it empty and keeps the old theme
fallback. The judgement is a histogram — inside a bubble the background is the
majority of pixels and the lettering the minority — which is why nothing assumes
comics are white and an inverted panel comes out black.

Verified on a device **in night mode**: before, the theme won and dark overlays
sat on a white page; now they are white, matching the page.

### Recognition is not deterministic, and that was destroying the result

Thirteen scans of one unchanged page produced line counts of 26, 27, 29 and 30,
and region counts of 20 through 23. No two agreed. Since element identity is
derived from recognised text, every scan produced different ids, so every scan
dropped the previous translations and re-requested them — the logs show
`hiding 8` followed by `showing 1`, over and over. **At most one translation was
ever on screen at a time.**

Re-recognising an unchanged page had been noted as wasted battery. It is worse
than that: it actively destroys the output. Scanning once per page fixes it by
never asking the question twice.

Measured, same static page, twenty seconds: **13 scans before, 1 after, and no
`hiding` events at all.** The counter-test matters as much — a page turn still
produces exactly one rescan, so this is "don't ask twice", not "stop asking".

### The capture includes our own overlays

A translation appearing is itself a change on screen, which the OCR path then
reads — and where an overlay covers its own source, the original text stops
being recognised, the element is dropped, the overlay is withdrawn, and the text
comes back. That oscillation is the flicker above, amplified.

`FLAG_SECURE` looks like the platform's answer: a secure window is documented not
to render on a non-secure display, and ours is non-secure. **Measured on device,
it blanks the entire mirror.** OCR fell to 2 lines — the status bar — and
`screencap` returned a fully black image, so it would have taken the user's own
screenshots with it. Reverted.

Overlays are separated from page turns by size instead. A translated page's
overlays come to roughly a tenth of the screen; a page turn changes nearly all of
it. The gap is wide enough to sit a threshold in, and unlike `FLAG_SECURE` it
costs the user nothing.

### Still open, visible in the current screenshot

- **The original shows through.** `0.8 × ours + 0.2 × theirs` — the ghost comes
  from the layer underneath and no amount of work on our layer removes it
  (ADR 008). Full opacity and touch passthrough remain mutually exclusive.
- **Translations still wear the source's footprint**, so a horizontal Chinese
  line is squeezed into a vertical column's width. Re-layout is the next item.
- **OCR reads browser chrome** along with the page. *(Fixed — see "Manga mode
  now reads only the page".)*

## Frames now come from the accessibility service

Screen sharing was the worst part of using V2. Every start of manga mode meant a
system consent dialog — Android 15 forbids reusing the token, so it never became
a first-run cost — plus a recording indicator for the whole session and a
`mediaProjection` foreground service. For a tool meant to disappear into
someone's reading, that ceremony was most of the experience.

`AccessibilityService.takeScreenshot()` needs none of it, and rides on the
permission V1 already required (ADR 009). MediaProjection is deleted; manga mode
now requires Android 11 and says so below it.

Measured on device, same page as before: **no dialog, no recording indicator,
and the translated page is identical** to the MediaProjection result. The
ongoing notification appears while the mode runs and clears when it stops, page
turns still trigger exactly one rescan, and `screencap` returns a normal image.

### What it cost, and what was done about it

The forced notification was a privacy feature, not a nuisance — it was what made
screen reading visible. Nothing forces one now, so Babel posts its own, and the
accessibility service description was rewritten to say that manga mode takes
pictures of the screen. Where the user has denied notifications there is no
indicator at all; the code logs that rather than passing over it.

### A testing trap worth remembering

`uiautomator dump` disconnects the accessibility service while it runs. Since the
service now hosts the whole pipeline, dumping the UI to check a result is what
destroys the result — manga mode reset to unavailable every time, which looked
like a product bug for several runs. Device state is read from `logcat` and
`screencap` instead.

## Translations now get the bubble, not the column

A recognised box hugs the lettering, and for vertical Japanese that is a narrow
column. Laying horizontal Chinese into it gave two or three characters a line —
legible, but plainly not what the page should look like.

The bubble around the text is the space actually available. `BubbleBounds` grows
the box outwards while the edge it would cross is still the sampled background
colour, which stops at the balloon's outline. Measured on the sample page, boxes
grew from roughly 100px wide to 210px, and the longest line went from three
lines of three characters to two lines of five. Translations are centred in the
bubble, as lettering is.

Three things this got wrong first, each caught by measurement:

- **A tolerance on the edge test let corners escape the bubble.** Allowing 20% of
  an edge's samples to be non-background put the box's corners outside an
  elliptical balloon — and since the overlay is painted in the bubble's own
  colour, a corner outside it erases part of the drawn outline. Every sample
  must now be clear. A box one step too small costs nothing; one that crosses
  the line damages the art.
- **Capping growth relative to the text rejected every real bubble.** A column of
  vertical Japanese is narrow and its balloon was seven times wider. The cap is
  now a share of the frame: nothing filling most of the screen is a speech
  bubble.
- **Growing all four sides at once settled into a tall sliver.** Each widening
  made the top and bottom edges longer, so they met the outline sooner, and the
  box kept the shape it started with. Width is what a horizontal translation
  needs, so width is now spent first — this alone took the longest bubble from
  three lines to two.

### Telling a bubble from a toolbar

Growing every box made browser chrome much worse: a small overlay over a tab
title became a large one, and the first device run of this change was visibly
uglier than what it replaced despite the bubbles being better.

A speech bubble encloses its text on all four sides. A toolbar or tab strip
encloses it above and below and runs off the screen sideways. So expansion that
reaches the frame edge, or the frame-relative cap, is read as *there was no
enclosure here* and the original box is kept. Chrome overlays went back to being
small; the bubbles kept their new size.

### Still open

- The original still ghosts through at 20%: `0.8 × ours + 0.2 << theirs` is a
  property of the layer underneath (ADR 008), not of anything we draw.
- A rounded address bar **is** an enclosure by this rule, so it grows. Consistent
  with the rule, and a reminder that the real answer to browser chrome is that a
  reader app is fullscreen.
- Manga mode reverts to off if the accessibility service is restarted — observed
  when the emulator killed the process under memory pressure. Safe, but silent.

## Acceptance

> V2 is complete when a mostly static comic page can be detected, OCR-processed,
> translated, and re-rendered **without rebuilding the V1 translation core**.

Measured end to end on `manga-page.html`, Android 15, device in dark mode:

| | Result |
|---|---|
| Detected | Scans only on change: 0 recognitions over 8s on a static page, exactly 1 per page turn |
| OCR-processed | 29 lines grouped into 20 regions, vertical Japanese in reading order |
| Translated | All four bubbles, on-device |
| Re-rendered | Bubble-width boxes, page-sampled backgrounds, text centred |
| Out of scope respected | 0 recognitions on the launcher, 7 on the comic page |
| No consent ceremony | No dialog, no recording indicator |

**The clause that mattered is the last one**, and it is the one worth a number.
Across the whole of V2, the V1 translation core changed by:

| File | Change |
|---|---|
| `DefaultTranslationCoordinator` | **+4 lines**, 0 removed — passes `SourceStyle` through, no logic touched |
| `DefaultLanguageResolver` | unchanged |
| `DefaultSensitiveContentPolicy` | unchanged |
| `MlKitTranslator` | unchanged |
| `InMemoryTranslationCache` | unchanged |

Everything else V2 needed arrived as new files under `domain/vision/` and two
new platform modules. Normalising every source into `TextElement` before the
pipeline (ADR 004) is what bought that: adding a second acquisition method with
completely different physics — pixels instead of nodes — cost the translation
core four lines of pass-through.

### What V2 does not do

Recorded so the state is not overstated:

- **The original ghosts through at 20%.** `0.8 × ours + 0.2 × theirs` is a
  property of the layer underneath (ADR 008). Full opacity and touch
  passthrough remain mutually exclusive.
- **Translation quality is limited by OCR**, not by the translator — 駅→統 and
  待→侍 were both observed on clean synthetic lettering.
- **A rounded address bar is an enclosure** by the bubble rule, so browser
  chrome still gets translated where it is boxed. The real answer is that a
  reader app is fullscreen.
- **Manga mode reverts to off if the accessibility service restarts** — safe,
  but silent.
- **Readable output on real pages is not there yet.** Measured against real
  material (below): the flatness criterion passes decisively, OCR passes on the
  inherited metric, and **ghost visibility fails**. The original and the
  translation end up legible at the same time, in the same bubble.

## Manga mode now reads only the page

Reported: with manga mode on, a comic page filled up with translations of things
that were not in any bubble.

The two paths never run together — manga mode suspends node scanning — but they
see different things, and that is the whole explanation. The text path reads the
accessibility tree, and a comic is an `<img>` with no text nodes, so on a comic
page it finds nothing and looks clean. Manga mode reads **the whole display as
pixels**, so it sees tab titles, the address bar and the status bar clock
alongside the artwork, and translates all of it. It was doing exactly what it
was told, on a screen that holds more than the comic.

### Excluding what the text path can see was not enough

The first rule tried was a definition rather than a guess: image translation
exists to read what the text path cannot, so anything accessibility already sees
is interface. It removed the address bar — and left the tab strip.

Measured: **Chromium exposes two text nodes for its entire window.** Its tab
titles are not among them. A rule that excludes what accessibility can see
cannot remove what accessibility cannot see.

A second attempt excluded every text node regardless of size, which did worse:
the browser reports a node of 1083x1383 — the whole content area — and treating
that as interface dropped every bubble on the page.

### Keeping only what is inside the content area

That oversized container is the answer rather than the problem. It is the page,
offset below the toolbar. Keeping only regions whose centre falls **inside** it
removes every kind of chrome at once — tab strip, address bar, system bars —
without naming any of them, and needs nothing the tree does not already expose.

Measured on the same page: 14 regions recognised, 9 dropped, 5 translated, and
the five are the bubbles. Tab strip, address bar and status bar are clean.

Where no such container is found nothing is restricted: a wrong guess would
silence the whole screen, and the failure has to be "translates too much", never
"translates nothing".

### Known limit

A reader that exposes its comic's text to accessibility would have that text
skipped, while the text path is suspended, so nobody translates it. Acceptable:
an app like that needs no manga mode. Recorded rather than left to be met later.

## Reading the page twice as large

You asked for OCR first, on the grounds that everything else is wasted if the
characters are wrong. The measurement that followed corrected two things about
how accuracy had been judged, and then found something worth taking.

### The yardstick was broken

Transcribed ground truth omitted punctuation while the recogniser returns it, so
a bubble read **perfectly** scored 66% because of two question marks. Every OCR
figure quoted before this was understated by roughly fifteen points. Punctuation
is now stripped from both sides before scoring; `ー` is kept, being a long vowel
inside words rather than punctuation.

Fixing the instrument before using it mattered: on the broken scale, contrast
enhancement looked competitive with enlargement. On the corrected one it is
clearly worse.

### The display was not the problem

Recognition runs on a screenshot, so a 1603x2048 page shown 1080 wide loses a
third of its size. That looked like the obvious culprit. Measured, it costs
almost nothing: 84% as displayed against 86% at full resolution. **The bottleneck
is the engine, not the capture.**

### What was tried, on two pages with hand-transcribed text

| Variant | Mean | `jap-mag-01` | `jap-mag-04` |
|---|---|---|---|
| Original file | 86% | 92% | 79% |
| As displayed *(the app's real input)* | 84% | 85% | 82% |
| **Enlarged 2x** | **89%** | **91%** | **87%** |
| Greyscale + contrast | 81% | 76% | 86% |
| Two-pass, magnified crops | 83% | 80% | 86% |

Only enlargement improved **both** pages, which was the rule set before looking:
the ground truth is thirteen bubbles, thin enough that a gain on one page alone
is more likely luck than progress. Contrast and the two-pass crop each helped
one page and hurt the other, and both were dropped despite sounding plausible —
the two-pass idea in particular was the one expected to win.

Adopted: enlarge the frame 2x before recognition, bounded by a pixel budget
because a doubled 1080x1920 frame is about 33MB held for the length of one
recognition. Boxes are divided back down; at 2x they would place every
translation in the wrong half of the page.

Measured after: `いいの？` and `先生？先生？` both went from partial to exact, and
on device `先生も汗拭きシート使いますか？` turned from "你使用老师或一位老师吗"
into "老师是否使用一个擦拭纸". Region and enclosure counts did not move.

### Still wrong, and not OCR's fault: one bubble split in two

`はい` is still separated from the bubble it belongs to, so that sentence is
translated twice in halves. The geometry, measured:

```
はい        x=137..170  y=242..308
いくらでも   x=86..125   y=295..455
gap 12px <= 58px           ✓
vertical overlap 13/66 = 19.7% < 25%   ✗
```

Real lettering is ragged — a two-character column above a long one barely shares
any vertical extent — and **no threshold separates that from two columns in
different bubbles**, because the two cases look identical to geometry.

**An attempt to let the pixels decide failed, measured.** The idea was that a
bubble has an outline while its interior does not, so sampling the gap between
two columns would show whether an edge lay across it. Two things went wrong:
sampling centre to centre runs through the strokes themselves and always fails,
and after fixing that to sample down the gap, it over-merged badly — 26 bubbles
became 11, with whole pages spliced into two regions. The space between two
*different* bubbles is frequently just as uniform as the space inside one: open
sky, a flat panel. "Nothing drawn between them" does not mean "same bubble".

Reverted. The split remains open, and it wants something that identifies the
enclosure itself rather than the space between columns.

### How much perfect bubble detection would actually buy

Before spending anything on a detector, `BubbleOracleExperimentTest` measures
the ceiling: bubbles given as measured rectangles, lines grouped by which one
holds them, lines in none discarded.

| Page | Today | Ceiling | Regions | Lines dropped as non-bubble |
|---|---|---|---|---|
| `jap-mag-01` | 91% | **94%** | 6 → 5 | 0 of 12 |
| `jap-mag-04` | 87% | **90%** | 9 → 8 | **3 of 21** |

**+3 points on each page**, which is less than the effort might suggest — and the
score understates it, because nothing here measures an opaque box sitting on a
sound effect. The three dropped lines on the second page are exactly `ヘラッ` and
the two fragments of cover lettering that currently get one.

What perfect detection does **not** fix is the rest: at the ceiling the pages
still score 94% and 90%, and every remaining error is a misread character —
`片械き` for `汗拭き`, `試略` for `試験`, `電葉` for `言葉`. That residue belongs
to the engine, and is roughly the same size as the gain from perfect grouping.

So the two candidates are worth about the same in text accuracy, and bubble
detection additionally fixes what the score cannot see.

Getting the oracle itself right took two attempts, both instructive. Deciding
grouping from the transcriptions discarded columns OCR had misread, charging
OCR's errors to grouping and producing a ceiling *below* the current result.
Loosening that then merged `先生?` from one balloon into another, because the
text appears in both — **no text comparison can separate two bubbles that say
the same thing.** Position separates them at once.

### Privacy finding: ML Kit logs recognised text itself

Our own diagnostics are clean — 100 `Babel.*` lines during a session, none
containing CJK. But ML Kit's **native layer** writes recognised text to logcat
under the `native` tag, outside our control.

Scope is limited: logcat is local and since Android 4.1 an app cannot read
another app's logs. The claim that text is translated on-device and not uploaded
still holds. It is recorded because it is a real difference between "we do not
log screen content" and "screen content is not logged", and because a release
build should be checked for the same behaviour before shipping.

ADR 008 defers the erasure decision to measurement rather than taste, so the
evaluation needs numbers, not impressions. Material is supplied locally and not
committed, for copyright reasons.

Measure three things:

1. **Share of bubbles whose background is not flat.** This decides whether
   inpainting is worth 30–200MB and the heat. Sampling a flat colour is
   equivalent to inpainting when the background is flat — see ADR 008 — so a low
   share settles the question.
2. **Ghost visibility on real art.** The residue computes to 204 grey on white.
   The question is whether it disturbs reading over screentones, dark panels and
   sound effects, not whether it is detectable in a screenshot comparison.
3. **OCR accuracy on real lettering.** The 83% from the probe was measured
   against Noto; published manga uses varied and often stylised fonts, so that
   figure should not be assumed to carry over.

A result is only a reason to change course if it names which of these failed.

## Results on real material

Six real pages, supplied locally and not committed. Two kinds: full-colour
digital manga with flat white balloons over painted art, and monochrome pages
with screentone. Measured by `MangaMaterialEvaluationTest` in
`:platform:capture`, which runs the actual pipeline components rather than an
imitation of them, plus end-to-end runs on the device in portrait.

### 1. Flat bubble backgrounds — **passes**

| | Regions | Median flatness | Below 60% |
|---|---|---|---|
| Enclosed (bubbles) | 26 | 85% | 1 (3%) |
| Open (no enclosure) | 3 | 80% | 0 |

One bubble in twenty-six is not flat enough for a sampled colour to stand in for
inpainting, and that one sits on screentone. **ADR 008's deferred question is
answered: inpainting is not worth 30–200MB and the heat.** The cheap path was
the right one.

### 2. Ghost visibility on real art — **failed, then fixed by setting the translation vertically**

The original failure is kept below because the reason it failed is the reason
the fix works. What changed is recorded under "Setting translations the way the
original was set".

#### The original finding

On the synthetic page the ghost was a curiosity. On real pages it makes the
result hard to read: in most bubbles the original and the translation are both
legible, overlapping.

The alpha cap is only half of why. The other half is that a real balloon holds
three to five columns, and the box grown from a text-hugging rectangle covers
only part of that. The synthetic page had two short columns and the overlay
happened to cover them, which hid the problem completely.

So this is not purely the platform limit from ADR 008. Part of it is ours: the
overlay does not cover the extent of the text it replaces.

### 3. OCR on real lettering — **remeasured; see "Reading the page twice as large"**

The figures below stand as originally recorded, and both the metric and the
input they used were wrong in ways that cancelled out to roughly the right
verdict for the wrong reasons. Corrected account follows further down.

| Page | Average character overlap |
|---|---|
| `jap-mag-01` (colour, clean lettering) | 98% |
| `jap-mag-04` (monochrome, screentone) | 80% |

Better than the 83% the feasibility probe found on synthetic lettering, which is
the opposite of what was expected.

**But the number is measured the way the probe measured it — character presence
anywhere on the page — and end-to-end output is much worse than 89% suggests.**
Characters are recognised; columns are still mis-segmented and mis-ordered, so
what reaches the translator is often scrambled. One bubble scored 20%: five
characters, one found.

A better measure would be per-bubble string similarity against the bubble's own
text, not set overlap against the whole page. Recorded rather than changed: this
pass was for measuring, and swapping the metric mid-measurement would make the
result incomparable with the probe.

### Three things the material showed that were not on the list

- **Output language is inconsistent.** The same page produced Chinese, English
  (`Wow ahead wipe-like!?`) and romaji (`Kedo`, `TRL BAITA`) in different
  bubbles, with the target set to `zh`. ML Kit pivots through English for
  non-English pairs, which would explain English leaking out when the second leg
  fails — **a hypothesis, not a diagnosis.** Not investigated in this pass.
- **A white page produces false enclosures.** `jap-mag-06` is a character sheet:
  a title and a bullet list on plain white, no bubbles at all. A 532×65 title
  grew to 824×441, because whitespace fenced in by artwork looks exactly like a
  bubble interior. Art text on a white panel — the book cover in `jap-mag-04` —
  gets the same treatment.
- **Sound effects were not translated, which is correct.** `グッ`, `パリ`,
  `ガシーン` were either not recognised or found no enclosure and kept their own
  bounds. That is the intended behaviour for out-of-scope text, and it held on
  real material.

## Setting translations the way the original was set

The orientation was never the missing piece — it was computed all along.
`TextRegion.orientation` is decided during grouping, and its own comment said
rendering would need it. It was dropped at the pipeline boundary, and the
renderer never knew. The wiring was a broken wire, not a missing mechanism:
`TextOrientation` moved to `:core:model`, `SourceStyle` gained a field, and the
coordinator needed no change at all because it already passes `element.style`
through.

`VerticalTextLayout` decides the type size and the columns; `VerticalTranslationView`
draws them, one character at a time, columns right to left. Android has no
vertical text — `TextView` has no writing mode — so the horizontal path keeps
its `TextView` and the two meet behind a small interface.

**This is what fixed criterion 2.** A vertical translation lands on the columns
it replaces instead of beside them, so the original is covered rather than
competing. Measured on the same colour page: every bubble now carries a legible
vertical Chinese translation, and the original reads as a faint tint behind it
rather than as a second text.

## The ghost is gone, and the coverage with it

Two defects reported from a device, on the same screenshot: panel one looked
"messy, two texts at once" and panel two was plainly misaligned.

**The misalignment was the box, not the drawing.** `BubbleBounds` grew a
rectangle one edge at a time while the whole edge was background, so any glyph
the recogniser missed sat on the candidate edge and stopped growth for good.
Measured on real pages: bubbles several times wider than their text grew by 9,
15 and 0 pixels. The translation then covered part of the bubble and the
original showed around it.

A flood fill was tried for this — lettering becomes a hole to flow around
rather than a wall — and **measured worse on real pages, so it was reverted**.
A balloon's tail is not a closed contour: the fill escaped through it and ran
across the page, one 67x145 column coming back 1553px wide. Two thirds of the
bubbles the blunter search had found were then lost, because an escaped fill
trips the frame check and is rejected outright.

| | Edge growth | Flood fill |
|---|---|---|
| Bubbles found | **26** | 9 |
| Rejected as unenclosed | 3 | 20 |

Bounding the flood's reach to a multiple of its own text did not rescue it: a
narrow column inside a large balloon needs a reach that also lets a leak cross a
panel. The coverage problem the flood was meant to fix therefore **remains
open** — a glyph the recogniser missed still blocks growth on that side — and
wants a different approach, not a tuned constant.

**The 20% residue was avoidable after all**, for manga, which this milestone and ADR 008
both previously said it was not. The cap applies to an untrusted overlay that
covers the screen while letting touches through; a bubble-sized window that
takes touches is neither. One window per translation, touchable: `dumpsys`
reports `mAlpha=1.0` against `0.8` before, and the original is genuinely
replaced.

Verified on a scrolling page with six translations on screen: a swipe between
them still scrolls. Only a touch landing on a translation is consumed, and
tapping one hides it so the original can be checked.

**This applies to manga only.** Applying it to V1 as well was a bug, reported
from a device within a day: V1's overlays are often large — a container node can
report the size of a whole page — and turning those into solid, touch-eating
blocks smothered the screen and broke touch passthrough, which is a V1
acceptance condition. The two paths now render differently because they need
different things, and V1's rendering is pixel-identical to its pre-change
baseline again.

**Punctuation is not rotated.** Real vertical typesetting turns `ー`, `「` and
`」` on their side. This does not. Recorded rather than left to be discovered.

## The language inconsistency, measured and fixed

The hypothesis was ML Kit pivoting through English. It was wrong, and the
measurement said so immediately. A diagnostic logging only language codes gave,
on one Japanese page:

| Detected source | Translations |
|---|---|
| `ja` | 1 |
| `en` | 2 |
| `fi` (Finnish) | 1 |

Source language was being **detected per element from OCR output**, and OCR
output is mangled enough that identification fails on it. A bubble read as
Chinese is worse than wrong: source equals target, so it is returned unchanged
and appears untranslated.

The fix is to stop guessing something already known. Manga mode reads with a
Japanese recogniser, so everything it produces is Japanese; `TextRecognizer`
now states its language and elements carry it. A source language the user chose
by hand still wins — this replaces guessing, not choosing.

Same page, after:

| | Before | After |
|---|---|---|
| Translations attempted | 4 | 13 |
| Attributed to Japanese | 1 | **13** |
| Failures | 3 | **0** |

## V1 was not polluted

The changes land in `:core:model`, the coordinator and the shared renderer, all
of which V1 uses, so V1 was re-verified rather than reasoned about.

The same page (`docs/testing/reading-sample.html`), the same four swipes, on a
build with the changes stashed and again with them applied:

- 7 text nodes on the first screen, both times — matching what V1 recorded
- No `ClearAll` during scrolling, both times
- **The rendered screen is pixel-identical below the status bar.** Compared
  programmatically, not by eye.

V1 elements carry no orientation and no declared language, so both new paths are
inert there — and the pixel comparison is what shows that rather than the
argument.
