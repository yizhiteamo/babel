## Acceptance testing method

Settled before V2 starts, so the work is not designed around a test that cannot
distinguish OCR from accessibility.

**Material must be an image.** `docs/testing/manga-page.html` contains nothing
but an `<img>` pointing at `manga-sample.png`. Live HTML text would be read
straight off the accessibility tree and the run would prove nothing about OCR.

Confirm this holds before trusting any result. The check is **not** "zero text
nodes" — the browser's own tab title and address bar are still text, and were
measured as 2 nodes. The judgement is that **no Japanese reaches acquisition**:
no node inside the page content area, and nothing containing kana or kanji.
Verified on device — both nodes were browser chrome, zero contained Japanese.

`manga-sample.png` is generated from `manga-source.html` by rendering it on
device and screenshotting, so it carries real glyph rasterisation rather than
synthetic shapes, without using copyrighted material. Real manga screenshots may
be used for judging quality, but are not committed.

Observe: bubbles detected, reading order, character accuracy, bounding-box
quality, and whether the masked area matches the sampled background.

## OCR feasibility (probed before V2)

`MlKitJapaneseOcrProbeTest` ran against the sample on the GMS-less emulator.

**Viable**: the Japanese recognizer runs without Google Play Services and does
read vertical text — 83% average character overlap across four bubbles.

**But its output cannot be used as translation units**, which shapes the
acquisition design:

- Columns are returned left-to-right; Japanese vertical text reads
  right-to-left. `今日はいい天気` came back as `いい天気今日は`.
- Bounding boxes are per column (38–95px wide), never per bubble. One bubble
  split into two blocks.
- Entire columns can be missed (`明日の会議`), and similar glyphs get confused
  (駅→統, 待→侍).

This confirms "text-region detection" and "speech-bubble-aware layout" are
load-bearing scope items: grouping columns into bubbles and rebuilding reading
order from box geometry is required work, not polish.

**Line granularity is sufficient.** A later probe printed `block.lines`, and
columns *are* separated there even when the enclosing block concatenates them
in the wrong order:

```
[3] box=(1156,122-1251,282) text=いい天気今日は      <- block, reversed
    line[3.0] x:1157-1193   text=いい天気
    line[3.1] x:1215-1251   text=今日は            <- further right, reads first
```

So reading order is fully recoverable from geometry, and `TextRegionGrouper`
does exactly that: group by adjacency, then sort columns by right edge
descending. Grouping also rejoins a bubble that arrived as two blocks.

One trap only real coordinates reveal: bubbles sharing a row are not aligned to
the pixel — the top-right bubble starts at y=122 while the top-left starts at
y=101. Ordering regions by top and then by right therefore reverses the page.
Rows are formed from vertical overlap first.

**The engine reports orientation directly.** `Text.Line.angle` came back as
88.6°–92.0° for every vertical column — a definite signal, so orientation is
never guessed. Shape (tall vs wide box) exists only as a fallback for
recognisers that report no angle, and is strictly weaker: a single character is
square and tells shape nothing, while its angle is just as clear.

`line.elements` turned out useless for this: ML Kit returns one element per
line holding the whole column, so character-level layout analysis is not
available.

Orientation is resolved **per line, not per page**. Comics mix vertical
dialogue with horizontal captions, and adjacency itself is orientation-
dependent — grouping the two together would corrupt the bubbles, not merely
their order.

**Known quality ceiling.** Desktop tools use manga-specific recognisers
(48px models, manga-ocr); ML Kit is general-purpose. If accuracy on real
material proves unacceptable, replacing the recogniser is a higher-priority
improvement than better erasure — a wrong character hurts reading more than a
faint ghost does.

## Screen capture

MediaProjection is not optional infrastructure that could be swapped for
something lighter — the platform dictates its shape:

- A projection cannot run outside a **foreground service** (Android 10+), and
  from Android 14 that service must declare `mediaProjection` as its type and
  hold `FOREGROUND_SERVICE_MEDIA_PROJECTION`.
- The service must reach the foreground **before** `getMediaProjection` is
  called; the reverse order throws.
- From Android 15 the user re-consents for **every** session and the token
  cannot be stored, so there is nothing to cache and no way to start capture
  silently.

The mandatory notification is a benefit rather than a cost here: it is the
user's standing indication that the screen is being read, which is what
`docs/systems/privacy.md` asks of anything touching screen content. Frames are
never written to disk and diagnostics log dimensions only.

Verified on device: session active at 1920x1080, virtual display created at 280
dpi, foreground service running with `types=0x00000020`
(`FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION`), a first frame actually retrieved,
and both service and virtual display released on stop.

The service performs a first-frame self check after starting, because a virtual
display can exist while its reader never fills — "session created" is not the
same as "frames arrive".

## Pipeline end to end

Capture → OCR → grouping → translation → rendering runs on device. Measured on
`manga-page.html`: 28 lines recognised in 19 regions, translations rendered over
all four bubbles. No change was needed in the translation core — normalising
every source into `TextElement` before it enters the pipeline (ADR 004) is what
made adding OCR an additive change.

**A static screen produces no frames.** `acquireLatestImage` returns null unless
the display changed, and a comic page is static by definition — reading on
demand works on video and fails on exactly the content V2 targets. Frames are
therefore cached from an `OnImageAvailableListener`, and `latestFrame` hands
back a copy because recognition is asynchronous and a new frame could recycle
the one being read.

**Both acquisition paths feed the same coordinator**, so accessibility scanning
is suspended while a capture session is active. Without that the same screen is
translated twice and two layers of overlays stack up.

### Known gaps, visible in the first end-to-end screenshot

Expected at this stage — erasure and re-layout are later items — but recorded so
they are not rediscovered:

- **Overlay colour does not match the page.** The device is in dark mode, so
  overlays render dark over a white comic page. This is precisely what ADR 008's
  background sampling is for, and it is not implemented yet.
- **Translations are squeezed into vertical column bounds**, two or three
  characters per line. "Translation re-layout" has to give a translated bubble
  the whole bubble, not the source column's footprint.
- **OCR reads the whole screen**, including browser chrome, so UI text gets
  translated alongside the comic.
- **Translation quality is poor** on these samples — partly OCR error
  (駅→統, 待→侍), partly on-device translation of short fragments. Consistent
  with OCR being the known quality ceiling.

## Sampling the background, and when to recognise at all

Overlays now take their colours from the page. The acquisition layer is the only
part of the system that ever sees pixels, so it samples them and passes them
down as `SourceStyle`; accessibility leaves it empty and keeps the old theme
fallback. The judgement is a histogram — inside a bubble the background is the
majority of pixels and the lettering the minority — which is why nothing assumes
comics are white and an inverted panel comes out black.

Verified on a device **in night mode**: before, the theme won and dark overlays
sat on a white page; now they are white, matching the page.

### Recognition is not deterministic, and that was destroying the result

Thirteen scans of one unchanged page produced line counts of 26, 27, 29 and 30,
and region counts of 20 through 23. No two agreed. Since element identity is
derived from recognised text, every scan produced different ids, so every scan
dropped the previous translations and re-requested them — the logs show
`hiding 8` followed by `showing 1`, over and over. **At most one translation was
ever on screen at a time.**

Re-recognising an unchanged page had been noted as wasted battery. It is worse
than that: it actively destroys the output. Scanning once per page fixes it by
never asking the question twice.

Measured, same static page, twenty seconds: **13 scans before, 1 after, and no
`hiding` events at all.** The counter-test matters as much — a page turn still
produces exactly one rescan, so this is "don't ask twice", not "stop asking".

### The capture includes our own overlays

A translation appearing is itself a change on screen, which the OCR path then
reads — and where an overlay covers its own source, the original text stops
being recognised, the element is dropped, the overlay is withdrawn, and the text
comes back. That oscillation is the flicker above, amplified.

`FLAG_SECURE` looks like the platform's answer: a secure window is documented not
to render on a non-secure display, and ours is non-secure. **Measured on device,
it blanks the entire mirror.** OCR fell to 2 lines — the status bar — and
`screencap` returned a fully black image, so it would have taken the user's own
screenshots with it. Reverted.

Overlays are separated from page turns by size instead. A translated page's
overlays come to roughly a tenth of the screen; a page turn changes nearly all of
it. The gap is wide enough to sit a threshold in, and unlike `FLAG_SECURE` it
costs the user nothing.

### Still open, visible in the current screenshot

- **The original shows through.** `0.8 × ours + 0.2 × theirs` — the ghost comes
  from the layer underneath and no amount of work on our layer removes it
  (ADR 008). Full opacity and touch passthrough remain mutually exclusive.
- **Translations still wear the source's footprint**, so a horizontal Chinese
  line is squeezed into a vertical column's width. Re-layout is the next item.
- **OCR reads browser chrome** along with the page. *(Fixed — see "Manga mode
  now reads only the page".)*

## Frames now come from the accessibility service

Screen sharing was the worst part of using V2. Every start of manga mode meant a
system consent dialog — Android 15 forbids reusing the token, so it never became
a first-run cost — plus a recording indicator for the whole session and a
`mediaProjection` foreground service. For a tool meant to disappear into
someone's reading, that ceremony was most of the experience.

`AccessibilityService.takeScreenshot()` needs none of it, and rides on the
permission V1 already required (ADR 009). MediaProjection is deleted; manga mode
now requires Android 11 and says so below it.

Measured on device, same page as before: **no dialog, no recording indicator,
and the translated page is identical** to the MediaProjection result. The
ongoing notification appears while the mode runs and clears when it stops, page
turns still trigger exactly one rescan, and `screencap` returns a normal image.

### What it cost, and what was done about it

The forced notification was a privacy feature, not a nuisance — it was what made
screen reading visible. Nothing forces one now, so Babel posts its own, and the
accessibility service description was rewritten to say that manga mode takes
pictures of the screen. Where the user has denied notifications there is no
indicator at all; the code logs that rather than passing over it.

### A testing trap worth remembering

`uiautomator dump` disconnects the accessibility service while it runs. Since the
service now hosts the whole pipeline, dumping the UI to check a result is what
destroys the result — manga mode reset to unavailable every time, which looked
like a product bug for several runs. Device state is read from `logcat` and
`screencap` instead.

## Translations now get the bubble, not the column

A recognised box hugs the lettering, and for vertical Japanese that is a narrow
column. Laying horizontal Chinese into it gave two or three characters a line —
legible, but plainly not what the page should look like.

The bubble around the text is the space actually available. `BubbleBounds` grows
the box outwards while the edge it would cross is still the sampled background
colour, which stops at the balloon's outline. Measured on the sample page, boxes
grew from roughly 100px wide to 210px, and the longest line went from three
lines of three characters to two lines of five. Translations are centred in the
bubble, as lettering is.

Three things this got wrong first, each caught by measurement:

- **A tolerance on the edge test let corners escape the bubble.** Allowing 20% of
  an edge's samples to be non-background put the box's corners outside an
  elliptical balloon — and since the overlay is painted in the bubble's own
  colour, a corner outside it erases part of the drawn outline. Every sample
  must now be clear. A box one step too small costs nothing; one that crosses
  the line damages the art.
- **Capping growth relative to the text rejected every real bubble.** A column of
  vertical Japanese is narrow and its balloon was seven times wider. The cap is
  now a share of the frame: nothing filling most of the screen is a speech
  bubble.
- **Growing all four sides at once settled into a tall sliver.** Each widening
  made the top and bottom edges longer, so they met the outline sooner, and the
  box kept the shape it started with. Width is what a horizontal translation
  needs, so width is now spent first — this alone took the longest bubble from
  three lines to two.

### Telling a bubble from a toolbar

Growing every box made browser chrome much worse: a small overlay over a tab
title became a large one, and the first device run of this change was visibly
uglier than what it replaced despite the bubbles being better.

A speech bubble encloses its text on all four sides. A toolbar or tab strip
encloses it above and below and runs off the screen sideways. So expansion that
reaches the frame edge, or the frame-relative cap, is read as *there was no
enclosure here* and the original box is kept. Chrome overlays went back to being
small; the bubbles kept their new size.

### Still open

- The original still ghosts through at 20%: `0.8 × ours + 0.2 << theirs` is a
  property of the layer underneath (ADR 008), not of anything we draw.
- A rounded address bar **is** an enclosure by this rule, so it grows. Consistent
  with the rule, and a reminder that the real answer to browser chrome is that a
  reader app is fullscreen.
- Manga mode reverts to off if the accessibility service is restarted — observed
  when the emulator killed the process under memory pressure. Safe, but silent.

### What V2 does not do

Recorded so the state is not overstated:

- **The original ghosts through at 20%.** `0.8 × ours + 0.2 × theirs` is a
  property of the layer underneath (ADR 008). Full opacity and touch
  passthrough remain mutually exclusive.
- **Translation quality is limited by OCR**, not by the translator — 駅→統 and
  待→侍 were both observed on clean synthetic lettering.
- **A rounded address bar is an enclosure** by the bubble rule, so browser
  chrome still gets translated where it is boxed. The real answer is that a
  reader app is fullscreen.
- **Manga mode reverts to off if the accessibility service restarts** — safe,
  but silent.
- **Readable output on real pages is not there yet.** Measured against real
  material (below): the flatness criterion passes decisively, OCR passes on the
  inherited metric, and **ghost visibility fails**. The original and the
  translation end up legible at the same time, in the same bubble.

## Manga mode now reads only the page

Reported: with manga mode on, a comic page filled up with translations of things
that were not in any bubble.

The two paths never run together — manga mode suspends node scanning — but they
see different things, and that is the whole explanation. The text path reads the
accessibility tree, and a comic is an `<img>` with no text nodes, so on a comic
page it finds nothing and looks clean. Manga mode reads **the whole display as
pixels**, so it sees tab titles, the address bar and the status bar clock
alongside the artwork, and translates all of it. It was doing exactly what it
was told, on a screen that holds more than the comic.

### Excluding what the text path can see was not enough

The first rule tried was a definition rather than a guess: image translation
exists to read what the text path cannot, so anything accessibility already sees
is interface. It removed the address bar — and left the tab strip.

Measured: **Chromium exposes two text nodes for its entire window.** Its tab
titles are not among them. A rule that excludes what accessibility can see
cannot remove what accessibility cannot see.

A second attempt excluded every text node regardless of size, which did worse:
the browser reports a node of 1083x1383 — the whole content area — and treating
that as interface dropped every bubble on the page.

### Keeping only what is inside the content area

That oversized container is the answer rather than the problem. It is the page,
offset below the toolbar. Keeping only regions whose centre falls **inside** it
removes every kind of chrome at once — tab strip, address bar, system bars —
without naming any of them, and needs nothing the tree does not already expose.

Measured on the same page: 14 regions recognised, 9 dropped, 5 translated, and
the five are the bubbles. Tab strip, address bar and status bar are clean.

Where no such container is found nothing is restricted: a wrong guess would
silence the whole screen, and the failure has to be "translates too much", never
"translates nothing".

### Known limit

A reader that exposes its comic's text to accessibility would have that text
skipped, while the text path is suspended, so nobody translates it. Acceptable:
an app like that needs no manga mode. Recorded rather than left to be met later.

## Reading the page twice as large

You asked for OCR first, on the grounds that everything else is wasted if the
characters are wrong. The measurement that followed corrected two things about
how accuracy had been judged, and then found something worth taking.

### The yardstick was broken

Transcribed ground truth omitted punctuation while the recogniser returns it, so
a bubble read **perfectly** scored 66% because of two question marks. Every OCR
figure quoted before this was understated by roughly fifteen points. Punctuation
is now stripped from both sides before scoring; `ー` is kept, being a long vowel
inside words rather than punctuation.

Fixing the instrument before using it mattered: on the broken scale, contrast
enhancement looked competitive with enlargement. On the corrected one it is
clearly worse.

### The display was not the problem

Recognition runs on a screenshot, so a 1603x2048 page shown 1080 wide loses a
third of its size. That looked like the obvious culprit. Measured, it costs
almost nothing: 84% as displayed against 86% at full resolution. **The bottleneck
is the engine, not the capture.**

### What was tried, on two pages with hand-transcribed text

| Variant | Mean | `jap-mag-01` | `jap-mag-04` |
|---|---|---|---|
| Original file | 86% | 92% | 79% |
| As displayed *(the app's real input)* | 84% | 85% | 82% |
| **Enlarged 2x** | **89%** | **91%** | **87%** |
| Greyscale + contrast | 81% | 76% | 86% |
| Two-pass, magnified crops | 83% | 80% | 86% |

Only enlargement improved **both** pages, which was the rule set before looking:
the ground truth is thirteen bubbles, thin enough that a gain on one page alone
is more likely luck than progress. Contrast and the two-pass crop each helped
one page and hurt the other, and both were dropped despite sounding plausible —
the two-pass idea in particular was the one expected to win.

Adopted: enlarge the frame 2x before recognition, bounded by a pixel budget
because a doubled 1080x1920 frame is about 33MB held for the length of one
recognition. Boxes are divided back down; at 2x they would place every
translation in the wrong half of the page.

Measured after: `いいの？` and `先生？先生？` both went from partial to exact, and
on device `先生も汗拭きシート使いますか？` turned from "你使用老师或一位老师吗"
into "老师是否使用一个擦拭纸". Region and enclosure counts did not move.

### Still wrong, and not OCR's fault: one bubble split in two

`はい` is still separated from the bubble it belongs to, so that sentence is
translated twice in halves. The geometry, measured:

```
はい        x=137..170  y=242..308
いくらでも   x=86..125   y=295..455
gap 12px <= 58px           ✓
vertical overlap 13/66 = 19.7% < 25%   ✗
```

Real lettering is ragged — a two-character column above a long one barely shares
any vertical extent — and **no threshold separates that from two columns in
different bubbles**, because the two cases look identical to geometry.

**An attempt to let the pixels decide failed, measured.** The idea was that a
bubble has an outline while its interior does not, so sampling the gap between
two columns would show whether an edge lay across it. Two things went wrong:
sampling centre to centre runs through the strokes themselves and always fails,
and after fixing that to sample down the gap, it over-merged badly — 26 bubbles
became 11, with whole pages spliced into two regions. The space between two
*different* bubbles is frequently just as uniform as the space inside one: open
sky, a flat panel. "Nothing drawn between them" does not mean "same bubble".

Reverted. The split remains open, and it wants something that identifies the
enclosure itself rather than the space between columns.

### How much perfect bubble detection would actually buy

Before spending anything on a detector, `BubbleOracleExperimentTest` measures
the ceiling: bubbles given as measured rectangles, lines grouped by which one
holds them, lines in none discarded.

| Page | Today | Ceiling | Regions | Lines dropped as non-bubble |
|---|---|---|---|---|
| `jap-mag-01` | 91% | **94%** | 6 → 5 | 0 of 12 |
| `jap-mag-04` | 87% | **90%** | 9 → 8 | **3 of 21** |

**+3 points on each page**, which is less than the effort might suggest — and the
score understates it, because nothing here measures an opaque box sitting on a
sound effect. The three dropped lines on the second page are exactly `ヘラッ` and
the two fragments of cover lettering that currently get one.

What perfect detection does **not** fix is the rest: at the ceiling the pages
still score 94% and 90%, and every remaining error is a misread character —
`片械き` for `汗拭き`, `試略` for `試験`, `電葉` for `言葉`. That residue belongs
to the engine, and is roughly the same size as the gain from perfect grouping.

So the two candidates are worth about the same in text accuracy, and bubble
detection additionally fixes what the score cannot see.

Getting the oracle itself right took two attempts, both instructive. Deciding
grouping from the transcriptions discarded columns OCR had misread, charging
OCR's errors to grouping and producing a ceiling *below* the current result.
Loosening that then merged `先生?` from one balloon into another, because the
text appears in both — **no text comparison can separate two bubbles that say
the same thing.** Position separates them at once.

## Stage 1: the manga models, measured on the desktop

Both remaining problems — bubbles and characters — have purpose-built models.
Before any Android work, they were run on the six pages and scored with the same
measure as everything else here.

**Licences were checked first, and one candidate was dropped on that alone.**
`comic-text-detector`, which several desktop tools use, is GPL-3.0 and would
take the whole app with it. `ogkalu/comic-text-and-bubble-detector` (Apache-2.0,
RT-DETR-v2, 11k comic pages, **10.6MB** int8) and manga-ocr (Apache-2.0, ONNX
int8, 83 + 28MB) were used instead.

### The detector

Its three classes are the three questions this milestone kept failing to answer:
`bubble`, `text_bubble`, `text_free`.

| Page | bubble | text_bubble | text_free |
|---|---|---|---|
| 01 | 8 | 8 | 0 |
| 02 | 5 | 5 | 0 |
| 03 | 4 | 4 | 1 |
| 04 | 8 | 8 | 0 |
| 05 | 2 | 2 | 3 |
| 06 *(character sheet)* | **0** | **0** | 2 |

Text sat inside a detected balloon for 4 of 5 hand-measured bubbles on page 01
and **8 of 8** on page 04. Page 06 has no balloons and it reports none — that is

### End to end, against the same transcriptions

| Page | Today | Perfect grouping (ceiling) | **Detector + manga-ocr** |
|---|---|---|---|
| `jap-mag-04` | 87% | 90% | **100%** |
| `jap-mag-01` | 91% | 94% | 87%* |

Page 04 reads **every bubble exactly** — above the ceiling, because the ceiling
was itself capped by ML Kit's character errors.

\* Page 01's lower figure is mostly **the transcription being wrong, not the
model**. The detector separates `……あ`, `先生？` and `はい` into their own
balloons, and looking again at the art, that is what they are; the ground truth
merged them. Its individual reads are near perfect —
`先生も汗拭きシート使いますか` and `そっちは私の使用済み` both exact, where ML Kit
gave `先生も比拭きシート`.

That leaves one real question rather than a defect: an utterance spread across
two joined lobes of one balloon now arrives as two translations. With actual
bubble boxes that is a far more tractable problem than it was with geometry
alone — overlapping boxes are easy to see.

Desktop timing: ~0.13s to detect, ~1–1.7s for a page of eight regions. Phone
latency is the next gate and is not yet measured.

Scripts and setup are in `tools/manga-model-eval/`; neither the models nor the
pages are committed.

## The translator, measured for the first time

Every complaint about translation quality until now was made on text the
recogniser had mangled, so it was never clear whose fault it was. With manga-ocr
reading the bubbles exactly, the same translator was given the real sentences.

**Clean input bought almost nothing.** The engine is the bottleneck:

| Japanese | ML Kit | Reference |
|---|---|---|
| 先生も汗拭きシート使いますか？ | 你用汗水表吗？ | 老师也要用擦汗巾吗？ |
| いくらでも使ってください | 请使用任何数字 | 请随便用 |
| 目を…閉じて… | 我的眼睛……关闭…… | 闭上眼睛… |
| …絶対に…動かないこと… | 绝对……没有移动…… | 绝对…不要动… |
| がんばりまーす!! | 祝你好运！ | 我会加油的！！ |
| 周囲が…店主の…言葉や誘導は無視して… | 周围的周围哭泣，噪音和逃脱…… | *(second half of the sentence dropped)* |

Some are fine — `いいの？` → 没关系吗？, `どんなことが書かれて` → 写的是什么. But
`いくらでも` ("any amount") read as "any number", and 目を閉じて ("close your
eyes") rendered as "my eyes close", are not input problems.

It is fast: 20–190ms a bubble after the first call. Fast and wrong is still
wrong.

Two things follow. Replacing the engine is worth evaluating, which was not
established before — it was assumed, then doubted, and is now measured. And
there is a cheaper thing to try first: the ellipses manga-ocr returns are passed
to the translator untouched, and `......あ` comes back empty. Normalising that
punctuation costs nothing and should be tried before a 75MB or 461MB model is
shipped to solve it.

Measurement lives in `CleanInputTranslationTest`.

## Stage 2: the models on a device

The worry was the recogniser's decoder. This export carries no key/value cache,
so every character re-runs it over the whole sequence; a desktop hides that cost
and a handset might not.

Measured on the emulator, all six pages:

| Page | Detect | Regions | Page total | Native heap |
|---|---|---|---|---|
| 01 | 376ms | 8 | **2.1s** | 477MB |
| 02 | 303ms | 5 | **2.1s** | 611MB |
| 03 | 210ms | 4 | **1.4s** | 611MB |

Page 06 returns **no regions at all**. It is the character sheet whose

### Memory is the real cost, and it is not small

Native heap reaches **613MB**, from 348MB once the three sessions are open. The
emulator survived; a phone under pressure might not, and this milestone has
already had one process killed that way. ORT's arena grows and does not give
memory back.

That has to be dealt with before this ships — session lifetime, arena
configuration, or holding one model at a time. Recorded as a cost rather than
waved through, because the timing figure alone would read as a clean pass.

### The port agrees with the desktop, nearly

Same model, same page, same characters — for all but one region.
`仕事中、突然視界が高くなったり…` came back with `増えたり` repeated and `舌`
where the desktop read `手足..色...声`. Android's bilinear resize is not PIL's,
and on a hard region that is enough to change the decode.

Everything else matches exactly, including `先生も汗拭きシート使いますか?`, which
the shipped pipeline reads as `先生も比拭きシート`.

Pages 02, 03 and 05 have no transcription, and produce long coherent sentences
that the current pipeline does not manage at all — for instance
`あ、あれ?マリー?懺悔室に入ったら出口があかなくなっちゃったんだけど......?`.

**The emulator is x86_64, not an ARM handset.** These numbers indicate a
direction; they are not phone numbers.

### Privacy finding: ML Kit logs recognised text itself

Our own diagnostics are clean — 100 `Babel.*` lines during a session, none
containing CJK. But ML Kit's **native layer** writes recognised text to logcat
under the `native` tag, outside our control.

Scope is limited: logcat is local and since Android 4.1 an app cannot read
another app's logs. The claim that text is translated on-device and not uploaded
still holds. It is recorded because it is a real difference between "we do not
log screen content" and "screen content is not logged", and because a release
build should be checked for the same behaviour before shipping.

ADR 008 defers the erasure decision to measurement rather than taste, so the
evaluation needs numbers, not impressions. Material is supplied locally and not
committed, for copyright reasons.

Measure three things:

1. **Share of bubbles whose background is not flat.** This decides whether
   inpainting is worth 30–200MB and the heat. Sampling a flat colour is
   equivalent to inpainting when the background is flat — see ADR 008 — so a low
   share settles the question.
2. **Ghost visibility on real art.** The residue computes to 204 grey on white.
   The question is whether it disturbs reading over screentones, dark panels and
   sound effects, not whether it is detectable in a screenshot comparison.
3. **OCR accuracy on real lettering.** The 83% from the probe was measured
   against Noto; published manga uses varied and often stylised fonts, so that
   figure should not be assumed to carry over.

A result is only a reason to change course if it names which of these failed.

## Results on real material

Six real pages, supplied locally and not committed. Two kinds: full-colour
digital manga with flat white balloons over painted art, and monochrome pages
with screentone. Measured by `MangaMaterialEvaluationTest` in
`:platform:capture`, which runs the actual pipeline components rather than an
imitation of them, plus end-to-end runs on the device in portrait.

### 1. Flat bubble backgrounds — **passes**

| | Regions | Median flatness | Below 60% |
|---|---|---|---|
| Enclosed (bubbles) | 26 | 85% | 1 (3%) |
| Open (no enclosure) | 3 | 80% | 0 |

One bubble in twenty-six is not flat enough for a sampled colour to stand in for
inpainting, and that one sits on screentone. **ADR 008's deferred question is
answered: inpainting is not worth 30–200MB and the heat.** The cheap path was
the right one.

### 2. Ghost visibility on real art — **failed, then fixed by setting the translation vertically**

The original failure is kept below because the reason it failed is the reason
the fix works. What changed is recorded under "Setting translations the way the
original was set".

#### The original finding

On the synthetic page the ghost was a curiosity. On real pages it makes the
result hard to read: in most bubbles the original and the translation are both
legible, overlapping.

The alpha cap is only half of why. The other half is that a real balloon holds
three to five columns, and the box grown from a text-hugging rectangle covers
only part of that. The synthetic page had two short columns and the overlay
happened to cover them, which hid the problem completely.

So this is not purely the platform limit from ADR 008. Part of it is ours: the
overlay does not cover the extent of the text it replaces.

### 3. OCR on real lettering — **remeasured; see "Reading the page twice as large"**

The figures below stand as originally recorded, and both the metric and the
input they used were wrong in ways that cancelled out to roughly the right
verdict for the wrong reasons. Corrected account follows further down.

| Page | Average character overlap |
|---|---|
| `jap-mag-01` (colour, clean lettering) | 98% |
| `jap-mag-04` (monochrome, screentone) | 80% |

Better than the 83% the feasibility probe found on synthetic lettering, which is
the opposite of what was expected.

**But the number is measured the way the probe measured it — character presence
anywhere on the page — and end-to-end output is much worse than 89% suggests.**
Characters are recognised; columns are still mis-segmented and mis-ordered, so
what reaches the translator is often scrambled. One bubble scored 20%: five
characters, one found.

A better measure would be per-bubble string similarity against the bubble's own
text, not set overlap against the whole page. Recorded rather than changed: this
pass was for measuring, and swapping the metric mid-measurement would make the
result incomparable with the probe.

### Three things the material showed that were not on the list

- **Output language is inconsistent.** The same page produced Chinese, English
  (`Wow ahead wipe-like!?`) and romaji (`Kedo`, `TRL BAITA`) in different
  bubbles, with the target set to `zh`. ML Kit pivots through English for
  non-English pairs, which would explain English leaking out when the second leg
  fails — **a hypothesis, not a diagnosis.** Not investigated in this pass.
- **A white page produces false enclosures.** `jap-mag-06` is a character sheet:
  a title and a bullet list on plain white, no bubbles at all. A 532×65 title
  grew to 824×441, because whitespace fenced in by artwork looks exactly like a
  bubble interior. Art text on a white panel — the book cover in `jap-mag-04` —
  gets the same treatment.
- **Sound effects were not translated, which is correct.** `グッ`, `パリ`,
  `ガシーン` were either not recognised or found no enclosure and kept their own
  bounds. That is the intended behaviour for out-of-scope text, and it held on
  real material.

## Setting translations the way the original was set

The orientation was never the missing piece — it was computed all along.
`TextRegion.orientation` is decided during grouping, and its own comment said
rendering would need it. It was dropped at the pipeline boundary, and the
renderer never knew. The wiring was a broken wire, not a missing mechanism:
`TextOrientation` moved to `:core:model`, `SourceStyle` gained a field, and the
coordinator needed no change at all because it already passes `element.style`
through.

`VerticalTextLayout` decides the type size and the columns; `VerticalTranslationView`
draws them, one character at a time, columns right to left. Android has no
vertical text — `TextView` has no writing mode — so the horizontal path keeps
its `TextView` and the two meet behind a small interface.

**This is what fixed criterion 2.** A vertical translation lands on the columns
it replaces instead of beside them, so the original is covered rather than
competing. Measured on the same colour page: every bubble now carries a legible
vertical Chinese translation, and the original reads as a faint tint behind it
rather than as a second text.

## The ghost is gone, and the coverage with it

Two defects reported from a device, on the same screenshot: panel one looked
"messy, two texts at once" and panel two was plainly misaligned.

**The misalignment was the box, not the drawing.** `BubbleBounds` grew a
rectangle one edge at a time while the whole edge was background, so any glyph
the recogniser missed sat on the candidate edge and stopped growth for good.
Measured on real pages: bubbles several times wider than their text grew by 9,
15 and 0 pixels. The translation then covered part of the bubble and the
original showed around it.

A flood fill was tried for this — lettering becomes a hole to flow around
rather than a wall — and **measured worse on real pages, so it was reverted**.
A balloon's tail is not a closed contour: the fill escaped through it and ran
across the page, one 67x145 column coming back 1553px wide. Two thirds of the
bubbles the blunter search had found were then lost, because an escaped fill
trips the frame check and is rejected outright.

| | Edge growth | Flood fill |
|---|---|---|
| Bubbles found | **26** | 9 |
| Rejected as unenclosed | 3 | 20 |

Bounding the flood's reach to a multiple of its own text did not rescue it: a
narrow column inside a large balloon needs a reach that also lets a leak cross a
panel. The coverage problem the flood was meant to fix therefore **remains
open** — a glyph the recogniser missed still blocks growth on that side — and
wants a different approach, not a tuned constant.

**The 20% residue was avoidable after all**, for manga, which this milestone and ADR 008
both previously said it was not. The cap applies to an untrusted overlay that
covers the screen while letting touches through; a bubble-sized window that
takes touches is neither. One window per translation, touchable: `dumpsys`
reports `mAlpha=1.0` against `0.8` before, and the original is genuinely
replaced.

Verified on a scrolling page with six translations on screen: a swipe between
them still scrolls. Only a touch landing on a translation is consumed, and
tapping one hides it so the original can be checked.

**This applies to manga only.** Applying it to V1 as well was a bug, reported
from a device within a day: V1's overlays are often large — a container node can
report the size of a whole page — and turning those into solid, touch-eating
blocks smothered the screen and broke touch passthrough, which is a V1
acceptance condition. The two paths now render differently because they need
different things, and V1's rendering is pixel-identical to its pre-change
baseline again.

**Punctuation is not rotated.** Real vertical typesetting turns `ー`, `「` and
`」` on their side. This does not. Recorded rather than left to be discovered.

## The language inconsistency, measured and fixed

The hypothesis was ML Kit pivoting through English. It was wrong, and the
measurement said so immediately. A diagnostic logging only language codes gave,
on one Japanese page:

| Detected source | Translations |
|---|---|
| `ja` | 1 |
| `en` | 2 |
| `fi` (Finnish) | 1 |

Source language was being **detected per element from OCR output**, and OCR
output is mangled enough that identification fails on it. A bubble read as
Chinese is worse than wrong: source equals target, so it is returned unchanged
and appears untranslated.

The fix is to stop guessing something already known. Manga mode reads with a
Japanese recogniser, so everything it produces is Japanese; `TextRecognizer`
now states its language and elements carry it. A source language the user chose
by hand still wins — this replaces guessing, not choosing.

Same page, after:

| | Before | After |
|---|---|---|
| Translations attempted | 4 | 13 |
| Attributed to Japanese | 1 | **13** |
| Failures | 3 | **0** |

## Manga mode was a global takeover, and it broke plain text

Reported from a device, after Stage 2: *in manga mode, switching between a comic
and plain text leaves bubbles behind and badly degrades the plain-text
translation.* Text mode on its own was fine.

Four separate defects, all growing from one assumption — that `mangaMode ==
ACTIVE` means the image path runs **everywhere**, and the node path runs nowhere.
A user does not stare at comics for the whole session, so plain pages fell into
a path written for artwork.

### What was actually wrong

1. **The image path never cleared on a change of screen.** The node path clears
   on a real window change (`lastWindowKey`); the image path had no equivalent.
   Turning from a comic to an article inside one app cleared nothing.

2. **Removal was left to a pixel threshold whose premise had expired.**
   `CHANGED_FRACTION = 0.30` was sized when overlays covered about a tenth of the
   screen. OCR overlays are now opaque windows and on a dense page cover most of
   it, so the threshold failed in both directions: a white comic followed by a
   white article did not reach 30% and was never rescanned — the bubbles simply
   stayed — while the opaque overlays themselves could exceed it and provoke
   rescans that produced different ids every time.

3. **Plain pages could not reach the node path.** `scanVisibleText` returned
   immediately whenever manga mode was on, so an article was OCR'd instead of
   read. `interfaceAreas()` only excludes label-sized nodes, and a paragraph is
   not label-sized, so the whole article was recognised and boxed.

4. **Every OCR result was stamped `ja`.** `TextRecognizer.language` was an
   unconditional `LanguageTag("ja")`, and the coordinator trusts a declared
   source language over detection. ML Kit's Japanese recogniser reads Latin too,
   so an English article was translated ja→zh. That alone would ruin plain text.

### The fix: ownership per screen, not per session

Manga mode now means image translation is *allowed*. Which path owns the screen
in front is decided on each pass by the rule the module already used for
regions — see `docs/systems/accessibility.md`.

The threshold was measured rather than chosen, as `LABEL_MAX_SCREEN_FRACTION`
and `CHANGED_FRACTION` were:

| Screen (Chromium, same device) | Labels inside the content area | Path |
|---|---|---|
| `comic-sample/jap-mag-01.html` | **0**, on every sample | image |
| `comic-sample/jap-mag-04.html` | **0**, on every sample | image |
| `reading-sample.html` | **8**, on every sample | node |
| `reading-sample.html`, mid-load | 1–2, briefly | image |

`MIN_CONTENT_LABELS = 3` sits in that gap. The mid-load reading is why it is not 1.

Three supporting changes were needed, and each closed a hole the first one
exposed:

- **`TextSourceEvent.Cleared` now carries its source.** It was source-blind, and
  `onCleared` dropped everything and emitted `ClearAll`. Harmless while the two
  paths were mutually exclusive for a whole session; with them alternating, one
  standing down would have wiped the other's live overlays.
- **A scan is dropped if its screen went away while it ran.** Recognition takes
  seconds. Without this, a clear issued mid-scan is undone by the scan that
  provoked it, and nothing is left to take the result down again.
- **A frame is only read once it has stopped moving.** The tree updates before
  the pixels do, so the first capture after a switch can still hold the outgoing
  page.

`MlKitTextRecognizer` now answers `languageOf(text)` instead of declaring one
language for everything, claiming `ja` only for text containing kana
(`JapaneseScript`). Han without kana is shared with Chinese and is left to
detection rather than claimed — the narrower rule costs nothing here, as all
fifteen transcribed bubbles contain kana.

### Measured on the device, before and after

Manga mode on throughout, alternating `jap-mag-0*.html` and
`reading-sample.html` in Chromium:

| | Before | After |
|---|---|---|
| Comic bubbles still on screen 2s after switching to the article | **3, opaque** | **none** |
| What translates the article | OCR, 27 lines boxed | node path, 7 text nodes |
| Article content bleeding onto the comic page | 2 black boxes of article text | none |
| Path chosen, over two full cycles | n/a | correct every time |

The last row is the one worth keeping: 0 labels → `recognised N lines`, 8 labels
→ `scanned …: 7 text nodes`, with no overlap.

### V1 re-verified

The changes land in `:core:model`, the coordinator and the service, all of which
V1 uses. With manga mode **off**, `reading-sample.html` reports 7 text nodes on
the first screen — the V1 baseline — no `ClearAll` during scrolling, and
scrolled content keeps translating in place.

## Manga mode was slow, and most of it was waiting

Reported from a device once the two paths stopped fighting: *the bubble
translation is slow to respond.* Measured before changing anything, switching
from an article to `jap-mag-01.html` in Chromium:

| Moment | Elapsed |
|---|---|
| Comic page present in the accessibility tree | — |
| Image path actually starts scanning | **3.0s, all of it idle** |
| `recognised 26 lines in 14 regions` | 2.0s |
| Translations on screen | 0.8s |

**5.9s, of which 3.0s was waiting on a fixed timer.** Two halves, 1.5s each: the
image path polled at `IMAGE_SCAN_INTERVAL_MS`, and the settled-frame check
sampled once per poll, so the first page after any change cost an extra full
tick before it could be confirmed still.

Two things were ruled out at the same time: the page is recognised **once**, not
repeatedly (no reading of our own overlays), and no time went on retries.

### What changed

**The image path now runs on the same events the node path does.** Its premise —
"a comic page fires no content-change event" — is false for the case that
matters: the log shows the node path reacting to the switch within 250ms while
the image path sat waiting for its timer. A second conflated channel, debounced
by the same `SCAN_DEBOUNCE_MS`, drives the same decision. The timer stays as a
fallback for apps that really are silent, and it stays at 1.5s: every tick costs
a full screen capture, so a faster timer would pay that forever.

**Settling is re-checked in 350ms rather than at the next tick.** The gate
itself is unchanged — it is what stops the outgoing page being read onto the
incoming one — but asking again quickly costs 0.35s where waiting for the tick
cost 1.5s. 350ms clears the platform's screenshot throttle of roughly one per
333ms; below that the capture just fails and the re-check learns nothing.

**Recognition reads the content area, not the display.** The regions outside it
were already being discarded as chrome — 14 of 18 on a comic page in a browser —
so recognising them was work thrown away. Cropping first cannot lose anything
the filter would not have dropped, which is what makes it safe to do before
reading rather than after.

### Measured, same route, same device

| | Before | Event-driven + fast settle | + content-area crop |
|---|---|---|---|
| Page on screen → recognised | 5.04s | 2.39s / 2.59s | **1.34s / 1.70s** |
| …of which capture | — | 763 / 754ms | 764 / 752ms |
| …of which recognise | — | 1588 / 1824ms | **595 / 932ms** |
| Translation (4 bubbles, parallel) | — | 0.27s | 0.31s |
| **Page on screen → translations visible** | **~5.9s** | ~2.7 / 2.8s | **~1.7 / 2.0s** |

Two pages, `jap-mag-01` and `jap-mag-04`, each figure from one run.

**Translation was never the problem.** It came to 150–310ms for a whole page,
running four bubbles concurrently with no queueing — worth knowing before Stage 3
swaps the engine, and worth having measured rather than assumed. The earlier
estimate of 0.8s came from reading screenshots, and was mostly the cost of taking
them.

### The crop did not cost accuracy

Bubble coverage on both pages is unchanged — every bubble visible on screen is
still translated. On `jap-mag-01` the reading of the largest balloon improved
(`先生も汗拭きシート使いますか?` went from garbage to `你使用老师或一位老师吗?`) and
the two halves of a split bubble came back as one. One observation on two pages,
so it is recorded as "no loss", not as a gain: the scoring harness measures the
recogniser on files, not this path.

### The properties from the previous round still hold

- A static page for 20s: **0** recognitions — no feedback loop
- The fallback timer still ticks at 1.52s with no events at all
- Scrolling re-triggers, and on the fast path the capture cost 16ms
- Manga ⇄ text over two cycles: ownership correct every time, no stale bubbles
- V1 with manga mode off: 7 text nodes on the first screen, 8 after scrolling,
  no `ClearAll`

## Stage 3, first step: the ellipses were eating the words

Manga dialogue is mostly ellipses, and manga-ocr reports them as it sees them:
`……` comes back as `......`, sometimes `..`, `・・・`, or a stray `:`. The
suspicion recorded earlier was that `......あ` "translates to empty". Measured,
that is **not** what happens, and the real behaviour is worse to look at: it
translates to `......`. The dots survive and the word does not, so a bubble the
recogniser read perfectly renders as punctuation.

### Four ways of handling it, measured against each other

Same provider, same fifteen hand-transcribed bubbles, on the device
(`TranslationExperimentTest`). The model download is timed separately — folding
it into the first bubble is how this harness previously timed out at 60s and
reported nothing.

| Variant | What it does |
|---|---|
| raw | the text as manga-ocr produced it |
| normalised | runs of dots collapsed to one `…` |
| stripped | normalised, ends split off, translated, reattached |
| fragmented | cut at **every** `…`, each fragment translated, ellipses rejoined |

| Bubble | raw | fragmented |
|---|---|---|
| `……あ` | `......` | **`…啊`** |
| `……先生?` | `......老师？` | `…老师？` |
| `どんなことが書かれて…` | `写的是什么......` | `写的是什么…` |
| `周囲が泣いたり…店主の…言葉や誘導は無視して…` | `周围的周围哭泣，噪音和逃脱......` — half the sentence gone | `当周围的哭泣，嘈杂和逃跑…店主…言语和指导忽略…` |
| `…仕事中、突然視界が…増えたり…手足…色…声が変化して…` | dots throughout | `…在工作期间，突然的愿景很高…增加…四肢…颜色…语音变化…` |
| `…絶対に…動かないこと…` | `......绝对......没有移动......` | `…绝对…impermanently…` — **worse**, English leaked |

Six of fifteen improved, one got worse, eight unchanged. `normalised` on its own
was close to neutral, and `stripped` fixed the ends but left lines whose ellipses
are in the middle — `目を…閉じて` still came back as `......关闭`, having lost the
eyes.

Total time went **down**, 1090ms → 952ms across the fifteen: shorter strings
translate faster, which more than pays for the extra calls.

### Where each half lives

Repair and splitting are separate jobs and they went to separate places:

- **`OcrPunctuation.normalize` runs in `CaptureTextSource`**, once, where the
  recogniser's mistakes are made. It is not applied to accessibility text, which
  is what the app actually wrote — the trailing-colon rule would turn a label
  reading `Name:` into `Name…`.
- **`FragmentingTranslator` wraps the provider**, splitting on real `…` only. It
  is provider-neutral, reports the provider's own id so cache keys are
  unaffected, and is inert for text without ellipses — which is nearly all
  accessibility text. V1 was re-checked and renders identically.

### What this did not fix

The five bubbles with no ellipses at all are word-for-word identical across all
four variants, and several are simply wrong:

| Japanese | ML Kit | Reference |
|---|---|---|
| `先生も汗拭きシート使いますか?` | 你用汗水表吗？ | 老师也要用擦汗巾吗？ |
| `いくらでも使ってください` | 请使用任何数字 | 请随便用 |
| `がんばりまーす!!` | 祝你好运！ | 我会加油的！！ |
| `あんまりわかんないケドッ` | Kedot不太了解 | 虽然不太懂啦 |

Punctuation repair fixes the damage punctuation was doing. It cannot make the
engine understand the sentence, and that is what the rest of Stage 3 is about.

## Stage 3, the engine question: Qwen2.5-0.5B measured, and ruled out

With punctuation handled, what is left is comprehension, and that is the
engine's. The plan named two candidates. Both assumptions in it turned out to be
wrong, in opposite directions.

### What is actually available

| Candidate | Size | ONNX ready | Licence |
|---|---|---|---|
| ML Kit (shipped) | ~30MB per language, downloaded on demand | n/a | Google terms |
| Qwen2.5-0.5B-Instruct `q4f16` | **483MB** | yes | Apache-2.0 |
| M2M100-418M `quantized` | **~632MB** (288 encoder + 344 decoder) | yes | MIT |
| opus-mt-ja-zh | ~75MB | **no export exists** | Apache-2.0 |

`shun89/opus-mt-ja-zh` holds PyTorch weights and sentencepiece models only —
there is no ONNX build of any opus-mt **ja→zh** anywhere on the Hub (ja→en
exists; zh does not). The plan's "~75MB int8 ONNX" was wrong. M2M100 was checked
as the nearest available narrow translator and is *larger* than the LLM, because
a 128k vocabulary makes for enormous embedding tables.

### Qwen2.5-0.5B, on the fifteen bubbles

Run on the desktop first, as the detector and manga-ocr were
(`tools/manga-model-eval/translate.py`).

**It is better at long sentences and much worse at short ones**, which is the
wrong way round for comic dialogue:

| Japanese | ML Kit | Qwen2.5-0.5B |
|---|---|---|
| `先生も汗拭きシート使いますか?` | 你用汗水表吗？ | **先生，您需要擦汗吗？** |
| `いくらでも使ってください` | 请使用任何数字 | **请随时使用。** |
| `目を…閉じて…` | 眼睛…关… | **闭上眼睛...** |
| `がんばりまーす!!` | 祝你好运！ | **加油！** |
| `どんなことが書かれて…` | 写的是什么… | 在这样的问题上，我们应当如何回答呢？ |
| `そっちは私の使用済み…` | 我用我的用过… | 这句日语的中文翻译是“这句是我的使用过”的英文翻译。 |
| `…あんまりわかんないケドッ` | …Kedot不太了解 | **我不会翻译日语，也不会参与翻译。** |
| `…あ` | …啊 | 哈哈 |

Four clearly better, five clearly worse, the rest a wash. The failures are not
mistranslations — they are an instruction-following collapse on short input: it
explains, refuses, or answers the sentence instead of translating it. A comic
bubble is short by nature, so this is a failure mode aimed squarely at the use
case, and no reference-scored average would have shown it.

### Speed is what actually decides it

**3.5s per bubble** on a desktop CPU; 51.8s for the fifteen. A page carries three
to eight bubbles, and the emulator runs ORT slower than this machine does.
Against a whole-page budget that now stands at **1.9s** — page on screen to
translations visible — this is two orders of magnitude out. No device
measurement was taken: the desktop figure already exceeds the budget by enough
that one would only confirm it.

For the record, ML Kit translates a whole page in 150–600ms, and its models
arrive per language rather than as one 483MB download.

### One finding worth keeping regardless of the outcome

`model_q4f16.onnx` **will not load on ONNX Runtime's CPU provider** with graph
optimisations enabled — layer-norm fusion fails on the fp16 constants. Disabling
optimisations works, at a cost in speed. q4f16 is a GPU/WebGPU build; anything
CPU-bound wants `int8` or `q4`. Recorded here because the same wall waits on a
phone's CPU provider, and Stage 4 would otherwise meet it twice.

### Where this leaves the engine question

Qwen2.5-0.5B is **not shippable**: too slow by 100×, 483MB, and it breaks on
exactly the short bubbles that make up most of a comic page. M2M100 is larger
still and unlikely to be worth its own measurement.

That leaves opus-mt-ja-zh — the only candidate in a sensible size class, and a
narrow translator that cannot refuse or ramble. It is also the only one that has
to be exported to ONNX before it can be judged at all.

## Stage 3 concluded: opus-mt-ja-zh beats ML Kit, and is the Stage 4 candidate

No ONNX build of opus-mt ja→zh exists, so one was made: `shun89/opus-mt-ja-zh`

- **`huggingface_hub`'s downloader sat at 0MB for twenty minutes** without

- A 310MB file did not arrive in one piece; the first attempt stopped at 28MB.

## What the unit of translation is worth — and a correction

A user compared this pipeline against GPT and found ours drifting badly. The
comparison carried a detail worth more than the verdict: **GPT was handed whole
balloons.** `はい いくらでも使ってください` went in as one line and came back as
one sentence. Every measurement in this document up to here used what manga-ocr
reads — `はい` and `いくらでも使ってください` **separately**.

Nothing translates `はい` on its own. So the earlier conclusion that engines
"collapse on short bubbles" confused two different things, and one of them was
our own input.

`BubbleScoring.groundTruth` settles the units: jap-mag-01 is five balloons read
as seven regions, jap-mag-04 is eight read as eight. The splitting is on the
first page only, which makes the experiment sharp.

### Joining helps one engine and hurts the other

| Balloon | | fragments | joined |
|---|---|---|---|
| `…あ` + `そっちは私の使用済み…` | ML Kit | `... \| 我已被使用过......` | **`......`** — everything lost |
| | opus fp32 | `a.- \| 这些是我使用的...` | **`咦,那是我用过的...`** |
| `はい` + `いくらでも使ってください` | ML Kit | `是的 \| 请使用任何数字` | `请使用它` |
| | opus fp32 | `Yes \| 请使用多少,多少。` | `拜托,请用好一点的。` |

**The garbage on tiny fragments was an artefact of splitting, not a weakness of
the model**: `a.-` and `Yes` vanish the moment the balloon is whole. That is the
correction — the earlier note that opus "breaks on exactly the short bubbles
that make up a comic page" had the cause wrong.

But ML Kit does not improve when given more; it gets worse, losing the whole
line on balloon 4. It is weak enough that context is not something it can use.

### So `FragmentingTranslator` stays, for as long as ML Kit does

Measured again at balloon level, ML Kit with and without it:

| Balloon | plain | fragmented |
|---|---|---|
| `…あそっちは私の使用済み…` | `......` | `…apo是我的使用…` |
| `目を…閉じて…` | `我的眼睛......关闭......` | `眼睛…关…` |
| `周囲が泣いたり…店主の…` | `当周围的环境哭了或冲走......` — half gone | `当周围的哭泣，嘈杂和逃跑…店主…言语和指导忽略…` |

Still a clear win. It compensates for a weakness this engine actually has. It
would become the wrong thing under opus, where joining is what helps — so it
belongs with the engine choice, not ahead of it.

### How close local can get, and what it costs

Best local configuration is opus-mt **unquantised, whole balloons**:

| Japanese | ML Kit (shipped) | opus int8 | opus fp32 | GPT |
|---|---|---|---|---|
| `先生も汗拭きシート使いますか?` | 你用汗水表吗？ | 老师也洗过手脚吗? | **老师也用擦汗纸吗?** | 老师也用擦汗湿巾吗？ |

### Where that leaves it

Grouping is worth fixing — but **for translation quality it only pays once the
engine changes**, because ML Kit cannot use the context. That reorders Stage 4:
the detector is an OCR-accuracy improvement first and a translation improvement
only in combination.

Reaching what GPT does is not available from an on-device model at any size this
project measured. That makes "should Babel be allowed to translate over the
network" a real question, and a product one — today the whole pipeline is
on-device and the app holds **no network permission at all**
(`docs/systems/privacy.md`).

## Scrolling, which had never been tested

A user asked whether manga mode had only ever been tried in portrait, and
whether scrolling a page that does not fit had been tried at all. Both answers
were no, and both were checkable:

- `docs/testing/push-comic-sample.sh:12` **rotates the device to portrait on
  purpose**, and `docs/milestones/v2.md` recorded "end-to-end runs on the device
  in portrait".
- `platform/capture/src/androidTest/` contains no `swipe` or `scroll` at all.
  Every manga test was "open the page, wait, screenshot".

So the reported scenario — landscape, a page taller than the screen, scrolling —
was uncovered. In landscape the sample page is scaled to 1920x2454 inside an
~870px viewport, so scrolling is not an edge case there, it is the whole
interaction.

### What it looked like

Measured before changing anything: a single swipe left three translations
sitting at their **old screen positions for 3.6 seconds**, over artwork they had
nothing to do with, while the untranslated bubbles that had scrolled into view
sat beside them untouched.

Two separate causes, and the second was not visible without the logs:

1. **Nothing takes the overlays down.** The image path's coordinates come from
   pixels, and the pixels moved. They only correct when a full rescan completes.
2. **`Screenshot: screenshot unavailable, code 3`.** The platform refuses a
   screenshot asked for too soon after the last
   (`ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT`), `scanOnce` treated the empty
   result as "no frame, give up", and scrolling fired requests faster than the
   interval. Two scan attempts were burned that way, and the page then waited on
   the 1.5s fallback timer — **2.2s of the 3.6s was this**.

### Both fixed

**`AccessibilityScreenshotSource` now waits out the interval** instead of
failing on it. It is the platform's constraint and this is the one class that
knows about the platform, so honouring it here spares every caller from
distinguishing "throttled" from "broken".

**A scroll takes the image path's translations down at once.** `TYPE_VIEW_SCROLLED`
gets its own conflated channel, deliberately not the one that goes through the
scan lock — taking overlays down must not queue behind a scan that is still
reading the screen the user has already left. Nothing restores them explicitly:
`clear()` resets the last recognised frame, so the next settled frame is
rescanned and they come back where they belong.

The node path is untouched by this, and must be: it reads fresh bounds from the
tree on the same event, which is why V1 scrolling was always fine. The signal is
guarded on the image path actually owning the screen.

| | Before | After |
|---|---|---|
| Stale translations over wrong content | **3.6s** | **none** — down on the scroll event |
| New translations in place | 3.6s | ~3.0s (debounce + capture + OCR) |
| `screenshot unavailable` during a scroll | 2 per swipe | none |
| Continuous scrolling | — | ends with every translation on its bubble |
| V1 scrolling | follows content | unchanged: no `ClearAll`, no hiding |

### A cost worth stating

Scrolling **back** to a bubble already translated does not reliably hit the
translation cache: OCR reads a partially-visible bubble differently, the text
differs, and the cache key differs with it. Measured — a scroll back produced
four fresh translations rather than four hits.

On-device that is only time. With a remote provider it is a request per scroll
(ADR 010). The bubble detector planned for Stage 4 is the thing that would fix
it properly, by finding whole bubbles instead of whatever the viewport happens
to show.

### Not covered by an automated test

*(Partly superseded: `SettleWindowTest` now covers the settling rule and
`ScrollReuseTest` the reuse and the cut-balloon skip. What remains untested is
`onAccessibilityEvent` itself.)*

The behaviour lives in `onAccessibilityEvent` and the platform's screenshot
throttle, neither of which a JVM test can reach and neither of which an
instrumentation test can drive without a live service and a real browser. It was
verified on the device and the reproduction is above: landscape, a comic page in
a browser, one swipe, and read `OverlayRenderer` in the log rather than taking
screenshots — repeated `screencap` calls load the device enough to change the
timings being measured, which cost one wrong reading before it was noticed.

## Stage 4, first step: the balloon detector on the device

The detector answers three separate complaints at once, which is why it comes
before the recogniser: grouping (one balloon, one unit of translation),
filtering (a sound effect is not a balloon), and placement (a balloon's outline
beats growing a rectangle until the pixels stop matching).

`ogkalu/comic-text-and-bubble-detector` — RT-DETR-v2, Apache-2.0, 10.6MB
quantised — now runs in the app rather than only in a benchmark.

### The seam

`PageReader` has two implementations and the choice is made by whether a model
is present, not by configuration:

- `GroupingPageReader` — read the whole page, group the lines by position. What
  V2 shipped, and still the path when there is no model.
- `DetectingPageReader` — find the balloons, read each one on its own.

Weights were not committed (`.gitignore`), so **absent was a normal state**: the
detector reported itself unavailable and the older path ran, verified by moving
the file away and watching the log.

> **Answered since (ADR 011).** How the file reaches a user's device was left
> open here, to be settled after the numbers. It has been: the detector now
> ships inside the package at 11MB, and manga-ocr is fetched on request. A
> pushed file still wins over the bundled one, so the command below keeps
> working for experiments.

```
adb push models/detector.onnx /sdcard/Android/data/com.babel/files/models/
```

### The balloon is a limit, not a replacement

First attempt used the detected balloon **as** the translation's bounds. On the
device that looked worse than what it replaced: the model reports a bounding
rectangle, and filling that opaquely covers the outline and the corners outside
an oval balloon.

Growing a box out from the lettering until the pixels stop matching produces a
rectangle that sits *inside* the balloon, which is the shape wanted — the two
methods are each better at a different half of the question. So `TextRegion`
carries the balloon as `enclosure`: the **limit** on that growth. It is also
what stops the growth leaking out through a balloon's tail, which is the failure
that had the flood-fill version reverted.

### Measured on the device, same page, same viewport

| | Grouping path | Detector path |
|---|---|---|
| Regions produced | 5 | 4 |
| Discarded as interface | 0 | **0 — it never finds chrome** |
| Recognition | 974ms | 1622ms |
| Detector load (once per session) | — | 250–400ms |
| Native heap / PSS | — | 225MB / 329MB |

Two things worth being straight about:

**It is slower.** Running the recogniser on four crops costs more than running it
once on the page, ~650ms more here. That buys correct grouping and correct
filtering, which is the trade this was chosen for — but it is a trade.

**Memory is not the problem Stage 2 feared.** That measurement — 348MB growing
to 613MB — was three sessions: the detector plus manga-ocr's encoder and
decoder. The detector alone is 10.6MB of weights and the process sits at 225MB
native. The memory question belongs to the recogniser step, not this one.

### Quality

On `jap-mag-01` the detector reports four balloons where the page draws four,
including reading `はい` and `いくらでも使ってください` as **two** — which the
hand transcription had merged, and which the artwork genuinely draws as two
separate balloons. The detector is right and the transcription was a convenience.

Translation quality is unchanged, because the recogniser is unchanged: ML Kit
still reads the crops, and still turns `先生も汗拭きシート` into `koisu`. That is
the next step.

## Stage 4, second step: manga-ocr reads the balloons

`kha-white/manga-ocr` via `ogkalu/manga-ocr-onnx` — Apache-2.0, 117MB across an
encoder and a decoder — now reads each cropped balloon, with ML Kit behind it.

The two are not interchangeable and the wiring says so: manga-ocr expects a
**cropped balloon** and would read a whole screen as one run-on string, so it is
reachable only through `DetectingPageReader`. The page-wide path stays on ML Kit
whatever is installed, which is what keeps "no models present" a working
configuration rather than a broken one.

### It reads correctly now

`先生も汗拭きシート使いますか?` used to come out of the pipeline as `koisu`.
It now translates to `你用汗水表吗？` — which is **exactly** what Stage 3 measured
for ML Kit given clean input.

That is the point worth taking: the recogniser is no longer the limit, and the
pipeline now sits where the Stage 3 experiment said it would. What is left —
`がんばりまーす!!` → `祝你好运！`, `…絶対に…動かないこと…` → `…绝对…impermanently…` —
is the translation engine, measured and documented separately.

### Memory was the real cost, and releasing fixes it

Stage 2's unresolved figure was 348MB growing to 613MB. Measured here with the
models loaded: **358MB native, 494MB PSS**. That is a process worth killing on a
smaller device.

`ImageTextScanner` gained `release()`, called when image translation is switched
off — the one moment we know it is finished with for now. Anything shorter (a
scroll, an app switch) comes back too soon to be worth a reload.

| | Native heap | PSS |
|---|---|---|
| Models loaded | 358MB | 494MB |
| After switching manga mode off | **49MB** | **182MB** |

Reloading costs 216ms for the detector and ~400ms for manga-ocr, verified by
switching off and on again and watching the page translate.

### A bug this uncovered, and it was not new

With manga-ocr in place the first page came back **blank** — eight balloons read,
nothing drawn, and then nothing for twenty-five seconds. The log said
`skipped: the same page as last read`.

`scanOnce` recorded the page as read *before* reading it. When the scroll guard
then dropped that reading — because a clear had landed mid-scan — the bookkeeping
still claimed the page was done, so it was never read again. A four-second scan
made the window wide enough to hit every time; with ML Kit's one-second scans it
had simply been rare.

`lastRecognized` is now written inside `publish`, under the same lock and after
the same guard, so a dropped reading leaves no trace of itself. The diagnostics
that found it — a line for each reason a scan is skipped — stayed in.

### Cost

| | Whole-page ML Kit | Detector + manga-ocr |
|---|---|---|
| Recognition, 8 balloons | ~1.0s | **3.8–4.2s** |
| Model load, once per switch-on | — | 216ms + ~400ms |
| Correct text | `koisu` | `先生も汗拭きシート使いますか?` |

Four seconds a page is a real cost and it is the next thing worth attacking —
the decoder has no key/value cache, so every character re-runs it over the whole
sequence. An export that carries one would change this number more than anything
else here.

## Where the four seconds go, and a correction

Eight balloons take 3.1–4.3s to read. Split per balloon:

| | Per balloon | Eight balloons | Shrinks with |
|---|---|---|---|
| Encoder | ~150ms, constant | ~1.2s | a smaller input |
| Decoder | 66–558ms, 11–50 steps | ~1.9s | a key/value cache |

The decoder's cost tracks its step count and the cost *per step* grows with the
sequence — 11 steps at 6ms each, 50 steps at 11ms each. That is the cacheless
decode showing itself: every character re-runs the decoder over everything
generated so far.

**No export with a cache exists.** `ogkalu/manga-ocr-onnx` ships the cacheless
decoder and nothing on the Hub carries `decoder_with_past` for this model, so
having one means exporting it — the same work the opus-mt evaluation needed.

### Reading balloons in parallel: measured, and the first reading was wrong

Balloons are independent and an ONNX session is safe to call concurrently, so two
at a time should be faster. It is:

| | Recognition | Native heap | PSS |
|---|---|---|---|
| One at a time | 3135ms | 517MB | **633MB** |
| Two at a time | **2399ms** | 554MB | **726MB** |
| Two at a time, one ORT thread each | 3021ms | 544MB | 652MB |

**The first version of this table was wrong** and nearly produced the wrong
decision. Sequential was measured at 494MB after *one* page and compared against
parallel after several, which attributed +230MB to concurrency. Measured fairly —
both on a fresh process after the same two pages — the difference is **+93MB for
−736ms**, not +230MB. ONNX Runtime's arena grows with use, so any memory figure
here only means something against an equally-worn process.

Capping ONNX Runtime to one thread per session was tried to claw the memory back.
It gave up most of the speed and returned little of the memory, so it is not a
middle option.

The pipeline stays **sequential** for now: the gain is real but modest, the cost
is on the axis this project has already had to work to control, and the
key/value-cache export is the change that would buy the time back without
spending any memory at all. The parallel version is a five-line change if that
judgement turns out to be the wrong way round.

## The recognition cache that does not work

A page is read from scratch after every scroll — eight balloons, 3.1s, each
time. Most of those balloons were on screen a moment ago. Caching recognition on
what a balloon *looks like* rather than where it sits therefore looked like the
best speed return available: it targets the actual reading behaviour rather than
saving a fixed fraction of one scan, it costs kilobytes instead of the 93MB that
parallel reading costs, and it would incidentally stop a scroll from re-billing a
remote translator (ADR 010).

It does not work, and three attempts say so.

### Attempt 1 — hash the crop

Exact equality over a downscaled luminance grid. Swept across grid sizes and
quantisation levels, on 27 balloons detected across the six sample pages:

| Grid | Levels | Distinct | Colliding | Survives a 1px shift |
|---|---|---|---|---|
| 8 | 2 | 27 | 0 | **3 / 27** |
| 8 | 16 | 27 | 0 | 0 / 27 |
| 16 | 8 | 27 | 0 | 0 / 27 |
| 24 | 16 | 27 | 0 | 0 / 27 |

Distinctness was never in doubt. Tolerance was: scaling resamples the whole
image, so a one-pixel shift of the source window nudges every output cell, and
with hundreds of cells it is near-certain that at least one crosses a
quantisation boundary.

### Attempt 2 — compare with a tolerance instead

If equality is too brittle, a threshold should do — that is what
`FrameChangeDetector` does for whole frames. It needs a gap: every balloon must
be closer to its own shifted self than to any other balloon.

| Grid | Worst self-shift | Closest other balloon | Gap |
|---|---|---|---|
| 8 | 35.4 | 13.1 | **−22.3** |
| 16 | 26.6 | 18.2 | −8.4 |
| 24 | 24.8 | 15.5 | −9.3 |

Mean absolute luminance difference per cell. The gap is negative everywhere: a
threshold loose enough to recognise a balloon that moved would also match a
different balloon, which is the collision that draws one balloon's words over
another. No tuning fixes a negative gap.

### Attempt 3 — trim to the lettering first

The failure looked like a framing problem rather than a content problem, so the
crop was trimmed to its ink before hashing — a wobbling box around fixed content
becomes fixed content. It helped, and not enough:

| Grid | Worst self-shift | Closest other | Gap |
|---|---|---|---|
| 8 | 10.9 (was 35.4) | 9.5 | **−1.4** |
| 16 | 20.8 (was 26.6) | 11.8 | −9.0 |

### What settles it

The shift test above is a worst case. The realistic one is two detections of the
same balloon across a real scroll, and it is worse:

> **5 balloons seen on both frames across a 120px scroll. 0 with an identical
> box. 0 matching signatures.**

The premise was that the detector makes a balloon a stable unit. It does not, and
the reason is inherent: the detector runs on a 640×640 resize of the **whole
screen**, so a screen that has scrolled is different input, and the box it
returns lands a few pixels differently every time. Nothing downstream of that can
recover a stable key.

`BubbleSignature` and `BubbleSignatureTest` stay in the test source set as the
evidence. Anything that revisits this needs to key on something the detector
does not produce — matching balloons between consecutive frames by position and
scroll delta, say — rather than on the pixels it hands over.

That last sentence turned out to be the answer. See *Attempt 4* below.

## The sentence split across balloons, measured

Page 07's five balloons are not noise and not five sentences. `PageTextDumpTest`
read them with manga-ocr, in reading order:

```
わたしの   めを見て   わたしの   めを見て   わたしの
```

`わたしの めを見て` — *look at my eyes* — cut in half, twice. Translated one
balloon at a time it arrives as 我的 / 看着我的眼睛, and the first balloon says
nothing.

Two candidates, and the cheap one had to be ruled out before the expensive one
could be justified:

- **context** — each balloon still its own request, with the group handed to
  DeepL's `context` parameter (read, not translated, **not billed**)
- **joined** — the group run together as one string, translated once

### Prefix-only context was wrong for the language

The first proposal was to give each balloon the balloons *before* it, which
keeps publishing incremental. A user pointed out why that cannot work here:
Japanese is verb-final, and the particle that fixes the meaning arrives at the
end. `わたしの` is decided by what follows it. Prefix context helps the half
that already reads.

### And full context does not work either

`BalloonContextExperimentTest`, against the real service, two context shapes —
the whole group, and only the neighbours:

| source | alone | ctx-whole | ctx-around | joined |
|---|---|---|---|---|
| `わたしの` | 我的 | 我的 | 我的 | — |
| `めを見て` | 看着我的眼睛 | 看着我的眼睛 | **眼睛** | — |
| `わたしのめを見て` | — | — | — | **看着我的眼睛** |

Context changed almost nothing, and where it changed anything it was worse.
`めを見て` with its neighbour as context came back as **眼睛** — the engine
dropped the verb, having taken the rest as already said. `いくらでも使ってください`
went from 请尽管用吧 to 请尽管**花**吧, spending money rather than using a towel.

That is what the parameter is for and what it is not: `context` disambiguates a
word sense. It does not let the engine emit words that belong to another
request. **So route A is dead, on measurement rather than on taste.**

### Joining is right — but only for genuine fragments

| group | alone | joined | better |
|---|---|---|---|
| `わたしの` + `めを見て` | 我的 / 看着我的眼睛 | 看着我的眼睛 | **joined** |
| `はい` + `いくらでも使ってください` | 好的 / 请尽管用吧 | 请尽管花吧 | **alone** — `はい` vanished |
| `......あ` + `そっちは私の使用済み...` | ......啊 / 那个是我用过的…… | ......那边的是我用过的…… | **alone** — `あ` vanished |
| `......先生?` + `先生?` | ......老师？ / 老师？ | ......老师？老师？ | equal |

Joining two *separate* utterances loses one of them. So the grouping rule is
load-bearing, and the one that fits is **syntactic incompleteness**: join a
balloon to the next only when it cannot stand on its own —

- `わたしの` ends in の, a dangling particle → join
- `はい` is a complete utterance → do not join
- `......あ` is an interjection → do not join
- `......先生?` ends in `?` → do not join

Four for four on the measured cases.

### What joining costs, and the part that has no clean answer

`RenderedTranslation` is emitted per `elementId`, so one result producing K of
them does not break the render contract — the change is confined to the
coordinator and to whatever decides the groups.

The unsolved half is **distribution**. `看着我的眼睛` has to go into two
balloons whose source was `わたしの` / `めを見て`, and no positional split
matches: Japanese orders it *[my][eyes look-at]*, Chinese *[look-at][my][eyes]*.
Splitting by source length gives 看着我 / 的眼睛, which is nonsense.

What does work is to stop treating the balloons as corresponding to source
fragments and treat them as **containers**: flow the joined translation through
the group's boxes in reading order, breaking where each box fills up and
preferring punctuation — the way a typesetter fills columns. `看着我的` /
`眼睛` reads correctly to someone taking the balloons in order.

The DeepL payload now carries `context` whenever a request has one. Nothing sets
it, and after this measurement nothing should; it stays so the experiment above
remains runnable against the real service.

## Joining the split sentence, built

Three pieces, each small, and none of them where the size of the problem
suggested they would be.

**Reading order.** The pipeline had none — the detector returns balloons in
whatever order the model emits them, which is invisible while each balloon is
its own sentence and is exactly what "join this one to the next" needs.
`MangaReadingOrder` bands by row and reads right to left; `DetectingPageReader`
now sorts by it before recognising. It also puts the incremental publishing in
the order a reader wants the page to fill in.

**Which balloons join.** `JapaneseClause.isUnfinished` — a line ending in a
case or linking particle is waiting for what follows. Two forms that look
unfinished are deliberately absent: `〜て` and `〜し` are usually whole lines in
dialogue (`めを見て` is an imperative, `目を…閉じて…` an instruction), and the
first draft included `て`, which would have joined two finished lines. The unit
tests hold all four measured cases.

`CaptureTextSource` holds an unfinished **balloon** and emits it with the next
one. Lettering on the artwork is excluded: reading order across panels is a much
weaker claim, and page 05's `私はたった今から` really does continue — two regions
later, not in the next one. A group is capped at three, and a page ending on an
unfinished balloon publishes it alone rather than losing it.

**One translation, several boxes.** Every balloon in a group is given the
*joined* text, so they agree on a cache key and the group costs one call. Each
carries a `TextShare`, and the coordinator shows it its part
(`SharedTranslation`): the translation is flowed through the boxes in reading
order, weighted by area, breaking at punctuation when there is any nearby. The
render contract is untouched — `RenderedTranslation` is still one per element.

## A chat model answers the reader, and two things that follow

The remote route was pointed at a chat endpoint (DeepSeek) and V1 and V2 were
run end to end against it. Every acceptance item passed, latency improved on
DeepL's — 0.5–0.8s against 1–2s — and prose came back noticeably better. Three
problems came with it, and only two of them were fixable.

### The address bar was translated, and the model replied to the reader

`file:///sdcard/Download/reading-sample.html` reached the provider like any
other node, and the answer was:

> I can't access files on your device. Please paste the text from the comic
> speech balloon directly into the chat, and I'll translate it into Chinese.

drawn in an opaque box over the address bar, on every page load. DeepL cannot do
this — ADR 010's "a narrow translator cannot refuse or ramble" naming the risk
that had now arrived.

#### The obvious guard does not work

A length ratio looked like the language-neutral way to tell a translation from a
speech: a refusal explains itself and should run long. Measured on real material
(`ChatAnswerExperimentTest`), it does not:

| kind | src | out | ratio |
|---|---|---|---|
| balloon `わたしの` | 4 | 2 | 0.50 |
| balloon `……あ` | 3 | 3 | 1.00 |
| prose, a whole paragraph | 153 | 42 | 0.27 |
| label `OK` | 2 | 2 | 1.00 |
| **the refusal** | 43 | 43 | **1.00** |

The refusal lands at 1.00, inside the legitimate range, not above it. **No
threshold separates them**, so that idea was dropped rather than tuned.

#### Two fixes, neither depending on the other

**The instruction now tells the model to echo.** Asked for something it cannot
translate — an address, a path, code, nonsense — it replies with the input
unchanged, and `translated == sourceText` is already reported as `Unchanged`,
which is never rendered. A refusal becomes a no-op instead of a caption. The
measurement showed the model half-does this on its own: a plain `https://…` and
a `host:port` already came back verbatim.

**And the address never leaves in the first place.** `DefaultSensitiveContentPolicy`
rejects a URL or an absolute path. Both halves of that class's reasoning point
the same way — nothing is lost by skipping an address, and what would otherwise
be sent is the user's browsing and their file names. It is the half that does
not depend on somebody else's model obeying an instruction, and it applies to
DeepL too, where it saves a request per page.

Deliberately narrow: a scheme or a leading slash. `example.com` stays
translatable, because it is as likely to be a word on a page, and `12:30` has to
stay a time.

### The language picker could not reach `zh`

`LanguagePickerDialog` put a `LazyColumn` in an `AlertDialog`'s text slot.
Dragging moved it about eight entries and then stopped; keyboard focus traversal
walked the whole list. On a phone that put everything after `id` out of reach —
**`ja`, `ko`, `ru` and `zh` among them** — and `zh` only worked because it is the
system default.

Fifty-odd short rows need no virtualisation, and the licences dialog in the same
file already scrolls as a `Column` with `verticalScroll`. Using the pattern that
already works here beat guessing at what the lazy one wanted. Verified by
scrolling to `zh` with a finger and selecting it.

### The untranslated word was **not** fixed

`apparently` sat in the middle of a Chinese sentence on page 08. The instruction
never asked for the whole reply to be in the target language, so a sentence
saying so was added.

It works on a clean transcription of that balloon and **not on the device**. Two
cold-cache runs produced the same Chinese with `apparently` still in it.

The reason is worth recording, because it is a mistake made twice in one day:
the experiment was first written against a *tidied* version of the balloon, and
reported a fix the device did not have. Against the recogniser's real output —
artefacts, missing spaces, a word cut off at the end — the answer changes again.
**A prompt constraint lowers the odds on clean input and does not settle it on
damaged input**, which is what OCR actually produces.

No programmatic check was added either. "Latin letters in a Chinese reply" would
reject `OK`, `iPhone`, and every name — a worse trade than the defect.

So this stays open, and belongs with the other engine residue: the recogniser's
errors are what the translator is reacting to.

## The untranslated word had two causes, and neither was the model

`apparently` sitting in the middle of a Chinese sentence was recorded as
unfixable model behaviour, after a prompt change worked in the harness and not
on the device. Both halves of that conclusion were wrong: there were two
defects, both ours, and both are fixed.

### One: the lines were glued together

`TextRegion.text` joined a region's lines with **no separator**, and its comment
gave the reason — Japanese columns continue one sentence, so a space would be
wrong. True for Japanese and wrong for everything else.

`PageTextDumpTest` was extended to print the lines before they are joined, and
every seam in the mangled English is a line boundary:

```
A succubus who | can't read a room | to save her life | you say hi and she
   ->  whocan't ... roomto ... lifeyou ... shestarts
```

Three balloons, eighteen lines, and nearly every corrupted word in them was made
by us. The translator had been guessing at words that were never on the page.

`LineJoin` now asks what meets at the seam: **either side written in a script
without spaces — Han, kana, Hangul — joins with nothing; otherwise a space.**
Orientation is the wrong test, because page 06's profile block is horizontal
Japanese and would take spaces it must not have.

Two grouper tests asserted the old glued output and were corrected. One of them
used `A`/`B`/`C` as stand-ins for vertical columns, which the new rule quite
properly spaces out; it now uses kana, which is what it always meant.

### Two: the target language was named as a code

Even with the input repaired the device kept `apparently`, while the same string
translated correctly in the harness. The difference was not the text. It was the
**target tag**:

| target sent | result |
|---|---|
| `zh-Hans-CN` | 而她显然会成为一位伟大的女巫 |
| `zh` | 而且她 **apparently** 要成为一名大女巫 |

The instruction said "into zh". A chat endpoint is asked in prose and a BCP-47
code is not prose; `zh` names Chinese with the script and region unsaid, and the
model hedged. `ChatTranslator` now names the language —
`Locale.getDisplayName` — so the instruction reads "into Chinese" or "into
Chinese (Simplified, China)".

**Which is why it only ever happened to some people.** Following the system
language gives the full tag; picking Chinese by hand in the picker gives bare
`zh`. The device had bare `zh` because the language picker had just been
tested by hand.

### The harness was lying, twice

Both rounds of this were prolonged by an experiment that did not reproduce the
device.

- The first version used a **tidied** transcription of the balloon and reported
  a fix the device did not have.
- The second read the page at **full size**, while the device reads a browser
  screenshot scaled to 1080 wide — a smaller picture, different stray marks.
- The third used `zh-Hans-CN` while the device carried `zh`, which turned out to
  be the whole remaining question.

`ChatAnswerExperimentTest` now carries the device's exact string and both tags,
and `PageTextDumpTest` reads pages at screen width. **An experiment that is
close enough to the device is not close enough.**

## The real device found a native crash the emulator never did

Reported from a Redmi K60 on HyperOS: the accessibility service switched itself

intermittently, and even with battery restrictions lifted. It read like an OEM

`adb logcat -b crash` on the phone:

`DefaultDispatch` is the dispatcher inference runs on. A native crash takes the
process, and Android switches off an accessibility service whose process dies
that way — **the two symptoms are one bug**, and the user re-enabling the
service by hand is the third.

### The race

`OnnxBubbleDetector` took the session under a lock and then used it **outside**
one:

```kotlin
val active = session() ?: return emptyList()               // lock held inside only
return withContext(dispatchers.default) { run(active, …) } // lock not held
```

while `release()` closed it under the lock. `MangaOcrRecognizer` had the same
shape with two sessions. The trigger is in the service: switching manga mode off
calls `imageScanner.release()` at once, and a page being read at that moment is
all it takes.

Inference now runs **inside** the lock that owns the session's life, so
`release()` cannot free what is being used. `Mutex` is not reentrant, so the
"fetch or load" step became a private function that assumes the lock is already
held. The cost is that `release()` waits for work in flight — 0.13s for
detection, up to a second for a balloon read — on a suspend function off the
main thread. Throughput is unchanged: balloons were already read one at a time.

### The test that had to be made to fail first

`SessionReleaseRaceTest` hammers detect and release concurrently. A native crash
cannot be asserted on, so reaching the end of the test is the assertion.

Its first version **passed against the buggy code**, which makes a guard worth
nothing. Launching the release alongside the detections was not enough: it
tended to run after they finished. Delaying it 30ms puts it inside the inference
window, and then it reproduces —

```
INSTRUMENTATION_RESULT: shortMsg=Process crashed.
adb logcat -b crash | grep -c libonnxruntime   →  7
```

— and passes with the fix, crash buffer empty. Every other instrumentation test
here calls these objects in sequence, which is why none of them could have found
this.

### Staying alive is a separate question, and now says so

The home screen gained a card, shown only once the accessibility service is on:
what "stops when you switch apps" looks like, and two buttons — the standard
battery-exemption intent, and the app's own settings page for autostart, which
has no public intent. Phrased from the symptom, because "allow background
activity" means nothing until you have watched translation stop.

`Killing … com.babel … due to SwipeUpClean` also appears in the phone's log:
that is the app being swiped out of recents, which is the system doing what it
was asked. The card covers it.

## Attempt 4 — match on where the balloon is, and it works

A user scrolling a webtoon: *"每移动一次都需要等待很久才会刷新翻译（即使该气泡已
经被翻译过的情况）"*. Measured on the device with a remote provider configured,
one swipe:

| | |
|---|---|
| Overlays removed | 292ms after the swipe |
| Settle + re-detect | 2.26s |
| **Reading 10 regions** | **4.31s** |
| All translations back | 7.1s |
| **Cache hits** | **2 of 10** — eight paid API calls |

Recognition dominates, and most of what it read had been read a moment earlier.
The three failed attempts above all hashed **what a balloon looks like**. This
one matches **where it is**, which is the thing the closing line named.

### The premise was measured before anything was built

`ScrollMatchMeasurementTest` scales a real webtoon to 1080 wide, takes
1700px-tall viewport windows 700px apart, and detects each window
independently — so the per-window resize jitter that killed attempts 1–3 is
present and not smoothed away.

| | Balloons still on screen | Matched |
|---|---|---|
| Five scrolls, total | 20 | **18** |

And the shift does not have to be supplied: every plausible pair votes for the
offset it implies, and the winner was right every time. The tolerance sweep
settled ±8px — ±16 and ±32 matched nothing more and only widen the chance of
pairing two different balloons.

**A correction to the first version.** It returned the winning *bucket*, and the
bucket is 8px wide, so the recovered shift was 696 against an actual 700 — every
time, in the same direction. That is rounding, not jitter, and it was spending
half the tolerance. Taking the median of the exact deltas inside the winning
bucket brought it to 701 against 700, and the reuse rate to the ceiling that the
known-shift column sets:

| | Recovered shift | Reused |
|---|---|---|
| Bucket | 696 (off by 4) | 18/20 |
| Median of the bucket | **701 (off by 1)** | **18/20**, at ±8 instead of ±16 |

### What it saves

`WebtoonScrollBenchmarkTest` runs the same six screens twice with the same
models: one reader across the scroll, versus a fresh reader per screen, which is
what the old code amounted to.

| Screen | Forgetting | Remembering |
|---|---|---|
| 0 | 2645ms | 2536ms |
| 700 | 2512ms | **1661ms** |
| 1400 | 2153ms | **1470ms** |
| 2100 | 2507ms | **1652ms** |
| 2800 | 3288ms | **2203ms** |
| 3500 | 3875ms | **2118ms** |
| **Total** | **16.98s** | **11.64s — 31% less** |

Same 52 regions either way; nothing is lost to get it. Roughly a third off every
scroll, the largest saving on the busiest screen.

The second half of the win is not in that table. A reused reading is the **same
string**, so the translation cache hits it — **18 of the 52 readings** across the
run, where re-reading produced 18 slightly different strings and 18 fresh
requests. That is the *cost worth stating* section above, finally answered.

**A correction to the benchmark.** Its first version built a whole new reader per
screen, which reloaded the ONNX sessions every time — a cost the old app never
paid, since the reader is a singleton. It reported 44%. Sharing the loaded models
and swapping only the reader around them is the honest comparison, and it is 31%.

### Where the line is drawn

- Two agreeing pairs minimum. One is a coincidence, and the cost of demanding
  two is one re-read on a screen with a single balloon.
- Size is part of the match, not a detail: two balloons of different sizes
  landing at the same height are not the same balloon, and reusing one for the
  other puts somebody else's words in it — worse than being slow.
- No horizontal tracking. A pan or a zoom is a different situation; there the
  votes fail to agree and everything is read again, which is where this started.
- A release forgets everything. Manga mode coming back on is a new screen.

### Tests

- `ScrolledBalloonsTest` (`:domain`, 10 cases) — the judgement, including every
  way a wrong match could be made.
- `ScrollReuseTest` (instrumentation, no models, no comic) — that the reader is
  actually wired to it. Verified to fail on the old behaviour: 6 reads where 4
  are expected.
- `WebtoonScrollBenchmarkTest`, `ScrollMatchMeasurementTest` — measurements.
  They assert nothing; a threshold on a timing fails on a loaded emulator rather
  than on a regression.

## 条漫的第二个问题：视口把气泡切成两半

用户提的：*"条漫是滚动的 可能会将原文截断，导致引入不必要的噪声"*。查下来完全
没处理——`OnnxBubbleDetector` 把每个框 `coerceIn` 到帧边界，半个气泡照读照译照上屏。

一次截断是四份损失：一次 encoder+decoder 白跑、一次接口调用白花、屏上一条半截
译文，以及**截断框高度和完整框不同，`ScrolledBalloons` 匹配不上，下一屏再付一次**。
上面那 18/20 里漏掉的 2 个，在 ±32px 下依然不匹配，而检测抖动是 4px 量级——
截断是唯一说得通的解释。

上沿被切是其中最坏的一种：那个气泡**上一屏已经完整读过**，碎片不带来新信息，
而碎片文本会生成不同的 id，于是正确的译文被摘掉、换成半截的。

### 先量

`ClippedBalloonMeasurementTest`，条漫走滚动视口、八张整页各读一次：

| | |
|---|---|
| 条漫贴边 | 52 个检测里 **9 个** |
| 其中能跟到下一屏的下沿框 | 3 个里 **2 个变高——真截断** |
| 整页漫画贴边 | **42 个里 0 个** |

所以这条规则在普通漫画上零代价，在条漫上摘掉约六分之一的检测。

**轮廓救不了。** 检测器同时给出气泡轮廓，轮廓完整在屏内本可证明里面的字是完整的。
量下来：9 个贴边框里，**没有一个**是「轮廓完整、只有字框贴边」——不是轮廓也被切，
就是压根没有轮廓。这个想法被数据否掉，没有进代码。

### 规则

跳过贴上沿或下沿的框，但**只在这一帧能恢复出位移时**。恢复不出位移就是首屏、
刚翻页、刚切进来——那时贴边的框可能真的完整（页顶第一个气泡），跳过会让它永远
不出译文。所以不可定位的帧完全按改动前的行为走，**这条规则不可能比今天更差**。

上下沿同时贴的照读：它比视口还高，等下去也不会完整，跳过就等于永不翻译。
样本里没有这种，留着是因为搞错的代价是一个永远静默不译的气泡。

### 收益

`WebtoonScrollBenchmarkTest`，同样六屏：

| | 每屏重来 | 跨滚动记住 + 跳过截断 |
|---|---|---|
| 合计 | 17.55s / 52 区域 | **9.85s / 44 区域** |
| | | **少 43%**（只有复用时是 31%） |

44 而不是 52 是有意的：少掉的 8 个是被切一半的气泡，推迟到显示完整的那一屏。
按上面的比例，其中约三分之一本来是完整的，只是晚一屏出译文。

### 测试

- `ClippedBalloonsTest`（domain）——尺寸取自测量值
- `ScrollReuseTest` 新增三例：截断不读、完整后再读、不可定位的帧照旧全读。
  **已验证在没有跳过逻辑时失败**（该读 3 次却读了 5 次）
- 这批测试的第一版 fixture 不真实：滚动后有气泡落在 `top = 3`、另一个整个跑到
  屏外，新规则正确地把它们当截断跳过，读起来却像回归。检测器不会报一个滚出屏幕
  的框，现在 fixture 也不报了。

## 往回滚也免费：记忆从「上一帧」扩到「整页」

上面那条 *A cost worth stating* 一直没解决：往回滚到一个已经翻译过的气泡，
不会命中缓存——OCR 对半可见的气泡读出的文本不同，缓存键跟着不同。
实测是四个已翻译的气泡产生四次全新翻译。

滚动复用第一版只记上一帧，所以往回滚照样全部重来。

### 改法

气泡改存**页面坐标**，每一帧对整份记忆投票，直接解出**这一帧的绝对页面偏移**。

关键在于不是把增量累加起来：每帧都是对原始页面坐标重新测一次，所以
**漂移不累积**。`theOffsetIsMeasuredAfreshAndDoesNotDrift` 连滚二十次再回到原处，
仍然一次都不用重读。

记忆保留视口上下各两屏，超出就丢；上限 120 条兜底。记忆越大，两个框偶然
互相吻合的机会越多，所以「留得少」同时是「更安全」。

### 顺带把投票算法改干净

分桶有两个毛病：返回的是桶，所以答案被向下取整最多 8px（实测 696 对 700，
每次都一样）；而真实位移压在桶边界上时，它会把自己的票劈成两半——票数最少
的时候恰恰最致命。改成「和自己相差不超过容差的邻居最多的那个 delta」，
两个毛病都没有，代码也不更长。

同时加了一条：若另一组相距超过容差的 delta 拿到同样多的票，返回 null。
框们没有就一个答案达成一致时，说「不知道」是诚实的回答——调用方于是重读整屏，
那只是慢；从两组里挑一组，则是把别人的话放进气泡。

### 缩放

用户问到的：缩放会不会让页面坐标失效。会，而且比「配不上」更糟——
偏移会停止更新，记忆变成一份按旧比例测的快照，等用户缩回原比例，
旧条目可能以**过期的偏移**重新配上。

处理办法不是去识别「这是一次缩放」，而是一条更短的不变式：

> **位移链一断，整份记忆丢掉。**

任何一帧投不出偏移就清空、从这一帧重新起链。缩放天然会触发它——3% 的缩放
放在 300px 的气泡上已经超出 8px 容差——翻页、切应用、转屏同理，都不需要各自
的分支。

没有做「相似变换」（缩放 + 平移的 RANSAC）。自由度从 1 涨到 3，配错的概率
随之上升，而配错的后果比慢严重。条漫按屏宽排版，捏合缩放的动机本来就低；
等量到「用户确实常缩放」再说。

### 收益

`WebtoonScrollBenchmarkTest` 新增一段：下滚三屏再原路返回。

| 返程屏 | 每屏重来 | 跨滚动记住 |
|---|---|---|
| 1400 | 2112ms | **205ms** |
| 700 | 2519ms | **210ms** |
| 0 | 1922ms | **211ms** |
| 全程七屏 | 16.25s | **6.44s，少 60%** |

返程剩下的两百毫秒是检测本身，一次识别都没有。

返程首屏是 5 个区域而不是去程的 6 个：这时已经知道自己在页面哪里，于是那个
贴下沿的气泡按 `ClippedBalloons` 推迟了；去程首屏定位不了，所以全读。

### 测试

- `ScrollReuseTest` 新增三例：往回滚不重读（**已验证只记一帧时失败**——
  该读 6 次却读了 9 次）、二十次滚动后不漂移、缩放前后都不复用
- `ScrolledBalloonsTest` 原有十例在换掉分桶后全部照旧通过

## encoder 批处理：量过，不做

条漫提速的第三条候选。成本表里 encoder 是每气泡约 150ms 且恒定——八个气泡
约 1.2s，占识别成本四成，而且是 KV cache 碰不到的那一半。可行性也是确定的：
`encoder_model_int8.onnx` 的 batch 维是动态的（`batch_size`），
`MangaOcrRecognizer` 只是硬写成了 `[1, 3, 224, 224]`。

`EncoderBatchMeasurementTest`：

| 批大小 | 逐个 | 批处理 | 原生堆 |
|---|---|---|---|
| 2 | 285ms | 294ms（**慢 3%**） | 228 → 228MB |
| 4 | 604ms | 583ms（快 3%） | 228 → **360MB** |
| 8 | 1190ms | 1142ms（快 4%） | 360 → 360MB |

encoder 是**算力受限**而不是调用开销受限：150ms 是实打实的算术，
`SessionOptions` 默认已经用满所有核心，合批没有剩下什么可赢的。
**+132MB 换 3%** 比它所类比的并发还差——并发是 +93MB 换 23%，当年就被否了。

所以不做，也不调参凑数。测试留在源码树里当证据，和 `BubbleSignature` 一样：
以后再想碰批处理，得先解释这组数字。

encoder 上真正的杠杆是更小的输入或换执行提供者（NNAPI / XNNPACK），
不是更宽的批——前者在模拟器上量不出有意义的数，要在真机上做。

## 被放弃的扫描不再读完整页

模拟器上端到端量到的：三次滑动里有一次，读满 9 个气泡花了 1997ms，然后因为
`clears` 在读的过程中前进而整份丢弃，重来只花 227ms（页面记忆救的）。
读取的总次数其实没变——被放弃那轮读到的都进了记忆，重来才会那么快——
但用户白等了那 2 秒，而且他真正在看的那一屏排在它后面。

`PageReader.read` 的回调从 `(TextRegion) -> Unit` 改成 `(TextRegion) -> Boolean`，
false 表示「这屏已经没人要了」。`CaptureTextSource` 本来就在算 `abandoned`，
现在把它作为返回值交出去。

提前收手不丢已读的：`thisPage` 里的条目照常进 `remember()`，替换它的那次扫描
仍然能复用。`ScrollReuseTest` 里两例守卫，**已验证在忽略停止信号时失败**
（该读 1 次读了 3 次）。

其中一例暴露了一个边界：只读了一个气泡就收手，记忆里只剩一条，下一帧的投票
凑不够两票（「一对是巧合」），于是整屏重读。真实页面上停止点远在这之后，
测试里把它写成两个气泡，并把原因记在注释里。

## 静止判定加了一行诊断

每次滚动之前必有一条 `skipped: the screen never came to rest`——滚动事件触发的
第一次扫描撞上还在惯性滑动的画面，`SETTLE_ATTEMPTS = 3`（约 1s 窗口）不够，
要等下一次事件或 1.5s 的 tick，白费约 0.3–0.5s。

想按「惯性滑动实际要多久才停」来定窗口，于是加了 `settled on look N after Nms`，
只在用了不止一次观察时才打（每次扫描都会静止，否则这行会以每 1.5s 一条的密度
淹掉别的）。**这次没能量到分布**——见下一节，模拟器上的滑动被译文窗口吃掉了，
页面根本没动。窗口大小因此还没改。

## 起点落在译文上的滑动会被整个吃掉

量条漫滚动时撞上的，反过来解释了此前一连串「页面纹丝不动」的测量。

| 手势 | 结果 |
|---|---|
| 起点 (900,950)，落在译文窗口 `[869,827][996,1081]` 内 | **页面完全不动** |
| 起点 (60,1000)，不在任何窗口内 | 正常滚动 |
| 同一点同一手势，关掉漫画模式 | 正常滚动 |

`docs/milestones/v2.md` 早先记过这个取舍——*"a swipe between them still scrolls.
Only a touch landing on a translation is consumed"*——当时译文稀疏，代价可以接受。
**条漫不稀疏。** 从 `dumpsys window` 量的那一屏：

| | |
|---|---|
| 译文窗口 | 9 个 |
| 覆盖面积 | 192071px = 屏幕的 **9.3%** |
| 起点落在拇指常用的中段（y 400–1500） | **10.5% 被吞** |

十次里有一次滑动毫无反应。用户会再滑一次——而「滑了没反应、再滑一次」在体感上
就是「等很久才出译文」。这很可能是用户那句抱怨里，除了旧版本之外的另一半。

还没修。可走的路：把可点击区域缩到一个角标而不是整个气泡、
或者把切换原文换成别的入口。哪条都是产品取舍。

## 漫画模式记住用户的选择

用户报过「关闭 Babel 后再次开启无障碍又得重新开启」。其中一半是系统行为，
另一半是我们的：`MangaModeController` 是纯内存的 `MutableStateFlow(CaptureState.IDLE)`，
进程一死就回到关闭。

改动本身不大，难的是**把「用户的决定」和「能力的变化」分开**。好在职责原本就是
干净的：`onServiceAvailabilityChanged()` 直接改 `_state`，从不调用 `stop()`，
所以 `stop()` 只可能由用户触发。于是：

- `activate()` 只移动状态，不表态（原 `start()` 的函数体，返回是否真的变成 ACTIVE）
- `start()` = `activate()` + 落盘 true，`stop()` = 原逻辑 + 落盘 false
- **只在真的变成 ACTIVE 时才记 true**：在 `UNSUPPORTED`/`UNAVAILABLE` 上点开启却
  记下来，会让它日后在用户被告知「这台设备用不了」的机器上自己启动
- 服务连上且状态为 IDLE 时读设置并 `activate()`——走 `activate()` 而不是 `start()`，
  否则每次服务绑定都回写一次

`MangaModeControllerTest` 加了五例，其中四例**已验证在没有持久化时失败**。
最要紧的一例是「服务断开不算用户关掉」：断开时不写设置，否则一次能力失效会在
日后被当成用户的同意重放。

### 隐私

进程恢复后应用会在用户没有再次触碰的情况下开始读屏，这条写进了
`docs/systems/privacy.md` 而不是只躺在代码里。支撑它的是四点：进程不是用户结束的、
只有用户的动作会被写下、恢复仍然需要他早已授予的无障碍权限、
以及常驻通知跟随 `CaptureState`，所以恢复出来的模式和手动开启的一样可见。

**顺带更正一处我自己的错误说法**：此前我说「只加了指引卡，没有前台服务，
全仓搜不到 startForeground」。前半句是错的——`MangaModeIndicator` 一直都在，
常驻通知一直都有；那次 grep 被 `head -5` 截断在 build 产物上了。
没有的只是前台服务，这一点仍然成立。

### 实机（模拟器）验证

装包 → 重绑无障碍 → 界面上开启漫画模式 → `am force-stop com.babel` → 重绑无障碍。
**没有任何点击**，日志里自己出现 `manga mode on`，`CaptureTextSource` 随即开始读屏。

## 静止判定的窗口：量过，维持原样

滚动路径上每一次滑动之前都有一条 `skipped: the screen never came to rest`，
看起来窗口太窄。

### 先修测量手法，两次

第一次测出来「每次扫描都是一次观察就静止」——因为**我做的滑动根本没滚动页面**，
起点落在译文窗口上被整个吃掉了。第二次给手势加了「前后截图不同就算滚动了」的
自校验，仍然是假的：**前后截图的差异来自 Babel 自己的译文被撤下又重绘**，
45 次扫描全是 `same page as last read`、一次读取都没有。

唯一可信的判据是日志里真的出现了读取。换成这个之后才拿到有效样本。

### 数据

上限放到 12，只统计页面真的动了的样本：

| 需要的观察次数 | 次数 | 最长 |
|---|---|---|
| 1 | 30 | <100ms |
| 2 | 2 | 514ms |
| 3 | 2 | 1015ms |
| **4** | **2** | **1541ms** |

从没需要过第 5 次。所以三次确实切掉了尾巴，把预算放到 1.8s 能让
`never came to rest` 归零。

### 归零了，但没变快

四次滑动一组，同样从页顶开始，从滚动事件量到第一条译文上屏：

| | 各次 | 均值 |
|---|---|---|
| 1.0s（现状） | 3.52, 3.58, 3.22, 2.65s | **3.24s** |
| 1.8s | 2.87, 4.38, 2.80, 3.54s | **3.40s** |

略慢，且落在噪声里。原因在日志而不在数字里：**滚动之后的第一次扫描无论如何都会
被作废**——惯性滑动会持续一秒多地发 `TYPE_VIEW_SCROLLED`，每个都清一次页面，
在途的扫描去发布时被丢掉。等得更久只是让注定作废的那次死得更晚，
并推迟了真正干活的那次。

所以维持原样。`SettleWindowTest` 留下来钉住这个上限，**包括它主动放弃的那一档**
（第 4 次观察才静止的页面留给下一个 tick）——这是静止判定这条路第一次有测试。

### 数据指向的下一步

不是「等多久」，而是「什么时候开始等」：`runImageEventLoop` 是从一串滚动事件的
**第一个**往后 250ms 就去扫描，而不是等到**最后一个**之后才安静 250ms。
改的是 `BabelAccessibilityService`，而且没量过——所以它是这里的一条记录，
不是一个凭感觉改掉的常数。

## 扫描等滑动结束再开始，而不是从第一个事件往后数 250ms

上一节的结论是「等得更久没用」，因为滚动后的第一次扫描无论如何都会被作废。
那就不该改「等多久」，该改「什么时候开始等」。

`runImageEventLoop` 原本是前沿防抖：拿到一串滚动事件的**第一个**，延迟 250ms
就去扫描。而惯性滑动会持续一秒多地发 `TYPE_VIEW_SCROLLED`，每个都让
`runImageScrollLoop` 清一次页面、推进 `clears`，在途的扫描发布时被丢掉。

改成后沿：拿到事件后只要还有新事件进来就继续等，安静 250ms 才扫描，
延长总预算 1.5s（否则一个不停发事件的页面会让事件循环永不触发，
而覆盖那种情况的正是 1.5s 的 tick）。

### 判断规则放在 `:domain`

`ScanDebounce.awaitQuiet` 不在服务旁边，是因为**它要能被测**：
`AccessibilityService` 在 JVM 测试里造不出来，而这个规则可以完全跑在
`runTest` 的虚拟时钟上。两个上限都用协程超时而不是读时钟——
`System.currentTimeMillis()` 不跟随虚拟时间，用它写的规则会让测试测不到东西。

第一版把上限写成「最多收几次」，测出来是错的：事件密集时每次只等 100ms，
六次就提前退出，一串 1 秒的事件在 600ms 处就返回了。改成外层总预算才对。

### 收益

四次滑动一组，同样从页顶开始，从滚动事件量到第一条译文：

| | 前沿（原先） | 后沿 |
|---|---|---|
| 各次 | 3.52, 3.58, 3.22, 2.65s | **2.38, 2.15, 2.04, 2.02s** |
| 均值 | 3.24s | **2.15s（少 34%）** |
| `abandoned part way` | **4 / 4** | **0 / 4** |
| 总读取次数 | 8 | **4** |

不只是快，还稳得多——区间从 2.65–3.58 收到 2.02–2.38。每次滚动省下的是一整次
白跑的检测加识别。

### 只改图像那条

节点通道的 `runScanLoop` 形状相同但没有动：读树又快又便宜，没有「扫描被作废」
这回事，而 V1 的时序是验收条件。回归验过——关掉漫画模式、打开文字页面，
节点译文照常上屏，`CaptureTextSource` 零活动。

### 测试

`ScanDebounceTest`（`:domain`，虚拟时间）五例：单个事件在安静期后返回、
一串事件只在停下之后才返回、永不停止的事件流在预算处返回、通道关闭立即返回、
安静期从**最后**一个事件起算。

接线本身没有单元测试——那是 `AccessibilityService`——**由端到端的
`abandoned part way` 从 4/4 降到 0/4 来验证**，这一点说清楚，不假装它被测了。
